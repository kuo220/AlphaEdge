# 指數期貨行情回補續跑（TF／ZEF／ZFF／TMF）

## Abstract

**背景／問題**：2026-09-02 20:16 起跑的五檔指數期貨日行情回補（`futures_price_daily`），在 2026-09-03 05:45 由使用者主動中斷。**TE 已完整補完**（27,446 筆 / 2,843 個交易日，2015-01-05 ~ 2026-09-02，與 MTX 的 2,843 天一致），**TF 補到一半**，**ZEF／ZFF／TMF 尚未開始**——這三檔表內目前只有 2026-08-27、08-28 兩天的驗證資料。整段回補全程零錯誤、零保險絲中止，中斷純粹是使用者需要關機。

**目標**：把 TF／ZEF／ZFF／TMF 四檔補齊到最新交易日，讓 `futures_price_daily` 的六檔指數期貨（TX／MTX／TE／TF／ZEF／ZFF／TMF）都有自上市日起的連續日行情，供期貨回測與 `futures_continuous` 使用。

**範圍界線（明確不做）**：
1. **不改 `core/` 的任何程式**。`FuturesPriceUpdater`／`FuturesPriceCrawler`／`FuturesPriceLoader` 在這次回補中表現正常，本工作只是把資料補完。
2. **不含 tick 與籌碼**。只補 `futures_price_daily` 這一張表。
3. **不含 2015 年以前**。起點一律 2015-01-01，再由 `clamp_to_listing_date()` 夾到各商品上市日。
4. **不重爬已入庫的區段**。續跑起點必須手動指定（見 S2 的陷阱說明）。

**驗收標準**：
1. S1~S4 全部 ✅。
2. 四檔的 `MAX(date)` 都等於執行當日的最近交易日，且 `COUNT(DISTINCT date)` 與各自上市日起的應有交易日數相符。
3. `updater.log_summary()` 的輸出中，四檔皆非「表內仍無資料」。
4. 回補期間 `logs/pipeline/update_futures_price.log` 的 `ERROR` 數為 0；若有保險絲中止，須在本文件記錄是哪一檔、哪一段。

## S1. 把殘留 CSV 掃進 DB（不重爬）✅

- **目的**：`FuturesPriceUpdater` 每 100 個交易日才入庫一次（`LOAD_BATCH_SIZE = 100`），中斷時最後一批未滿 100 天，那些 CSV 已下載但還沒進 DB。**先掃這一批，續跑起點才會正確**——否則會白白重爬約 40 天。
- **做法**：

  ```bash
  cd /Users/kuofuyu/program_project/AlphaEdge
  source .venv/bin/activate
  python -c "
  from core.pipeline.tw.loaders.futures_price_loader import FuturesPriceLoader
  FuturesPriceLoader().add_to_db()          # 不帶 only_dates ＝ 掃全目錄
  "
  ```

  入庫走 `INSERT OR IGNORE`（主鍵 `(date, product, expiry, session)`），已入庫的列會靜靜跳過，掃全目錄是安全的。
- **產出**：`data/db/tw_futures.db` 的 `futures_price_daily`。
- **驗證方式**：輸出的統計行 `[futures_price] 入庫完成：新寫入 N 檔、已存在跳過 M 檔、失敗 0 檔`，且 **失敗必須是 0**。若非 0，多半是中斷時 `to_csv()` 被打斷留下的半截檔——刪掉統計行列出的那個檔再跑一次即可。
- **相依**：無。

> **✅ 執行紀錄（2026-09-03 05:48）**
> - 程序 PID 59662 於 05:46 停止（連續執行 9 小時 31 分，`ERROR` 0，最後爬到 TF 2024-04-08）。
> - 掃描結果：`[futures_price] 入庫完成：新寫入 57 檔、已存在跳過 17,170 檔、失敗 0 檔`。
> - TF 由 2,202 天前進到 **2,259 天**，最新日 **2024-04-08**，沒有半截 CSV。
> - 故 **S2 的 TF 續跑起點為 `2024-04-09`**，已填入下方腳本。

## S2. 續跑 TF 🔄

- **目的**：TF 是 1999 年就上市的金融期貨，2015-01-01 起約 2,860 個交易日，是四檔裡最長的一段。
- **做法**：

  1. **先查實際進度**（S1 完成後才查，否則會少算最後一批）：

     ```bash
     sqlite3 data/db/tw_futures.db \
       "SELECT MAX(date) FROM futures_price_daily WHERE product='TF' AND date<'2026-08-01';"
     ```

     **`date<'2026-08-01'` 這個條件不可省**——見下方陷阱說明。

  2. 把查到的日期 **+1** 填進腳本的 `PRODUCT_START_DATES["TF"]`，只留 TF 一檔，執行。

- **陷阱：絕對不可以改成 `resume=True`** ⚠️

  `get_actual_update_start_date()` 取的是該商品的 `MAX(date)`，而 TF／ZEF／ZFF／TMF 表內都有 **2026-08-27、08-28 兩天的驗證資料**。`resume=True` 會把起點算成 **2026-08-29**，然後印一句「已是最新」直接跳過中間整段缺口，**不會有任何錯誤訊息**。這就是回補起點一律手動指定的原因。

- **產出**：`futures_price_daily` 的 TF 列。
- **驗證方式**：`SELECT COUNT(DISTINCT date), MIN(date), MAX(date) FROM futures_price_daily WHERE product='TF';` 的 `MAX(date)` 為執行日最近交易日，天數與 TE 的 2,843 天同量級（TF 與 TE 同為日盤＋夜盤、同一組交易日曆）。
- **相依**：S1。

## S3. 回補 ZEF／ZFF／TMF 🔄

- **目的**：三檔都還沒開始，表內只有驗證列。
- **做法**：起點一律傳 `2015-01-01`，由 `clamp_to_listing_date()`（commit `cc978a1`）夾到各自上市日——ZEF 2021-06-28、ZFF 2021-12-06、TMF 2024-07-29。**不要自己算上市日填進去**，夾住的邏輯已經在 `core/config` 的 `FUTURES_PRODUCT_LISTING_DATES` 維護。
- **產出**：`futures_price_daily` 的三檔列。
- **驗證方式**：三檔 `MIN(date)` 各等於其上市日後的第一個交易日、`MAX(date)` 為最近交易日；`log_summary()` 無「表內仍無資料」。
- **相依**：S1（S2 可與本步驟合併成同一次執行，見〈續跑腳本〉）。

> **🔄 執行紀錄（2026-09-03 17:40 起跑）**
> - 四檔於同一次執行中依序跑：`TF → ZEF → ZFF → TMF`，`end_date` 為 2026-09-03。
> - 開跑前確認：`certifi` 指向 `~/program_project/AlphaEdge/.venv/...` 且檔案存在、系統無殘留爬蟲程序。
> - 首行 log 為 `########## TF: 2024-04-09 ~ 2026-09-03 ##########`，與 S1 推得的起點一致。
> - 預估 8.5~10.5 小時；**期間不可闔上筆電**（見〈預估耗時〉末段）。

## 續跑腳本

原腳本放在 session 的 scratchpad（`/private/tmp/...`），**該目錄會被清掉**，故全文抄錄於此。存成任意路徑後以專案的 `.venv` 執行即可（`python backfill_price.py`）。

`PRODUCT_START_DATES` 只留還沒補完的商品。**S1 已執行完畢，TF 的起點 `2024-04-09` 已經是最新值，可直接跑**；若中間又跑過任何一次回補，再照 S2 第 1 步重查一次。

```python
"""指數期貨行情回補（續跑）

**起始日一律用 resume=False 明確指定**：表內這幾檔都有 2026-08-27~28 兩天的驗證
資料，`resume=True` 會把起點算成 2026-08-29 而跳過中間整段缺口，且只會顯示
「已是最新」，不會有任何錯誤訊息。

ZEF／ZFF／TMF 傳 2015-01-01 即可，由 `FuturesPriceUpdater.clamp_to_listing_date()`
夾到各自的上市日（cc978a1）。
"""

import datetime

from loguru import logger

from core.pipeline.tw.updaters.futures_price_updater import FuturesPriceUpdater

PRODUCT_START_DATES = {
    # S1 已於 2026-09-03 05:48 執行完，表內補到 2024-04-08，故由隔日起跑
    "TF": datetime.date(2024, 4, 9),
    "ZEF": datetime.date(2015, 1, 1),  # 夾到 2021-06-28
    "ZFF": datetime.date(2015, 1, 1),  # 夾到 2021-12-06
    "TMF": datetime.date(2015, 1, 1),  # 夾到 2024-07-29
}

if __name__ == "__main__":
    updater = FuturesPriceUpdater()
    end_date = datetime.date.today()
    done, aborted = [], []

    for product, start_date in PRODUCT_START_DATES.items():
        logger.info(f"########## {product}: {start_date} ~ {end_date} ##########")
        try:
            updater.update_product(product, start_date, end_date, resume=False)
            done.append(product)
        except ValueError as error:
            # 保險絲（連續 N 天查無資料）只代表這一檔有問題，其餘商品照跑
            logger.error(f"########## {product} 觸發保險絲：{error} ##########")
            aborted.append(product)
        except Exception:
            # 其餘例外多半是環境層級的（TLS 憑證、磁碟、DB 連線），對每一檔都會
            # 立刻重演一次。2026-09-02 專案目錄被搬走時就是這樣：五檔在同一毫秒
            # 各自「中止」，看起來像五個獨立問題，實際上是同一個。整批停下來。
            logger.exception(
                f"########## {product} 遇到非保險絲的錯誤，整批中止 ##########"
            )
            raise

    logger.info(f"########## 完成：{done}；保險絲中止：{aborted} ##########")
    updater.log_summary(list(PRODUCT_START_DATES))
```
