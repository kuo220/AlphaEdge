# 策略層資料欄位抽象化

## Abstract

- **背景／問題**：`core/api/*.py` 一律回傳 SQLite 的 raw `pd.DataFrame`，而資料表欄位名是中文（`core/pipeline/loaders/stock_price_loader.py:57-74` 的 `"收盤價"`、`"成交股數"`、`"開盤價"`）。策略層因此直接對 raw DataFrame 取中文字面值——`momentum_strategy_1.py:98`、`_2.py:95`、`_3.py:94`、`_4.py:82`、`_5.py:91`、`overnight_lead_event_strategy.py:120` 共 6 支策略、10 餘處。`StockQuote` 這層 model 已經存在，但策略要取「昨收」「N 日前成交量」時仍繞過它去打資料庫原始 schema。
- **目標**：策略層**不再出現任何資料庫欄位字面值**。策略取用歷史資料一律透過 API 的具名方法或正規化後的欄位常數，使「資料表長什麼樣」成為 `core/api/` 以下的實作細節。
- **範圍界線**：**只改讀取路徑**——不改資料庫 schema、不改 ETL 寫入端、不改任何交易邏輯與參數門檻。**不做**：把中文欄位改成英文欄位的 DB migration（屬 [PostgreSQL遷移計畫.md](PostgreSQL遷移計畫.md)）、不做 `StockQuote` 的欄位擴充、不碰 `frontend/`。
- **驗收標準**：`grep -rn '"收盤價"\|"開盤價"\|"成交股數"\|"投信買賣超股數"' core/strategies/` 結果為 0；`test_long_regression_snapshot`（915 筆 × 13 欄）逐筆相同；`tests/` 全數通過。

> **為什麼要提前做**：現況的失效模式是**靜默**的。`momentum_strategy_1.py:98` 用 `df.loc[mask, "收盤價"].empty` 判斷，欄位一旦更名會直接拋 `KeyError`；但 `_5.py:91` 一類的寫法在資料缺漏時走的是同一條 `continue`，換資料源後**策略會安靜地不開倉而非報錯**。這種錯誤在回測報表上只表現為「訊號變少」，極難察覺。

## 盤點結果

| 檔案 | 行號 | 觸及欄位 | 用途 |
|------|------|----------|------|
| `momentum_strategy_1.py` | 98、101 | `收盤價` | 取前一交易日收盤價算漲幅 |
| `momentum_strategy_2.py` | 95、99 | `收盤價` | 同上（Tick 模式仍用日 K 取昨收） |
| `momentum_strategy_3.py` | 94 | `收盤價` | 取區間收盤序列 |

## S1. 盤點觸點並定案做法 ⬜

- **目的**：先定案抽象化的層級，S2 之後才有明確目標；三種做法的成本與影響面差很多。
- **做法**：三選一——

  - **做法 A（最小改動）**：只把中文欄位名收斂成 `PriceColumn.CLOSE` 之類的常數，策略層仍自行操作 DataFrame。
    - 優點：改動極小，一天內可完成。
    - 缺點：**沒有真正解決抽象洩漏**——策略仍依賴「回傳的是 DataFrame」「要自己建 mask」，換到 PostgreSQL 或美股資料源時仍要全面改。

  - **做法 B（推薦）**：常數化 ＋ **API 層提供具名查詢方法**，策略只呼叫方法、不碰 DataFrame 欄位。
    - 優點：欄位名與資料結構同時被封裝；`core/api/` 成為唯一知道 schema 的地方，與 [回測引擎多市場抽象.md](回測引擎多市場抽象.md) Phase2-5 的 `DataFeed` 方向一致。
    - 缺點：要新增約 6~8 個 API 方法並補測試。

  - **做法 C（治本但昂貴）**：直接把資料表欄位改成英文，ETL 寫入端一併改。
    - 缺點：需要 DB migration ＋ 重跑歷史資料，且會同時影響 `frontend/` 與既有 `.db` 檔。**本文件不採用**，該議題歸 [PostgreSQL遷移計畫.md](PostgreSQL遷移計畫.md)。

  **建議做法 B**：它讓策略層與 schema 解耦，但不需要動任何既有資料，且做法 C 日後真的要做時，做法 B 已經把改動面縮到 `core/api/` 一層。
- **產出**：本文件 §盤點結果 補完；本節補上決策段落與理由。
- **驗證方式**：清單與 `grep -rn '收盤價\|開盤價\|成交股數\|投信買賣超股數' core/strategies/` 的結果逐條對得上。
- **相依**：無。

## S2. 欄位名常數化 ⬜

- **目的**：讓「資料表欄位名」在全專案只有一處定義，S3／S4 的 API 方法與既有 loader 共用。
- **做法**：於 `core/pipeline/utils/constant.py` 新增欄位常數，依 `CLAUDE.md` §2.7「先定義 module-level `UPPER_SNAKE_CASE`，再由 `class XxxEnum(str, Enum)` 引用」：

  ```python
  # 定義 price 資料表欄位常量
  PRICE_COL_OPEN: str = "開盤價"
  PRICE_COL_HIGH: str = "最高價"
  PRICE_COL_LOW: str = "最低價"
  PRICE_COL_CLOSE: str = "收盤價"
  PRICE_COL_SHARES: str = "成交股數"


  class PriceColumn(str, Enum):
      """price 資料表的中文欄位名（DB schema 專用，不外流到策略層）"""

      OPEN = PRICE_COL_OPEN
      ...
  ```

  同時把 `core/pipeline/loaders/stock_price_loader.py` 的 `CREATE TABLE` 與 `core/pipeline/cleaners/` 內的字面值改為引用常數。
- **產出**：`core/pipeline/utils/constant.py`、`core/pipeline/loaders/stock_price_loader.py`、`core/pipeline/loaders/stock_chip_loader.py`。
- **驗證方式**：既有 ETL 測試（`tests/test_db_tables.py`、`tests/test_stock_margin_cleaner.py`）通過；`CREATE TABLE` 產生的 schema 與改動前逐欄相同。
- **相依**：S1。

## S3. `StockPriceAPI` 新增具名查詢方法 ⬜

- **目的**：把「建 mask → 取欄位 → `.iloc[0]`」這段重複六次的樣板收進 API，策略只表達意圖。
- **做法**：於 `core/api/stock_price_api.py` 新增方法，覆蓋 §盤點結果 的全部用途：

  | 方法 | 用途 | 對應現況 |
  |------|------|----------|
  | `get_close(stock_id, date) -> Optional[float]` | 單日單股收盤價 | `_1.py:101`、`_2.py:99`、`_4.py:84` |
  | `get_volume_lots(stock_id, date) -> Optional[int]` | 單日單股成交量（張） | `_4.py:85`、`_5.py:91` |
  | `get_close_series(stock_id, start_date, end_date) -> pd.Series` | 區間收盤序列（index 為 date） | `_3.py:94`、`overnight_lead_event_strategy.py:120` |
  | `get_close_map(date) -> Dict[str, float]` | 單日全市場收盤價對照表 | 取代「整張 DataFrame ＋ 逐檔 mask」的 O(n²) 樣式 |

  - **找不到資料一律回傳 `None`／空 `Series`**，不要拋例外，維持與現況 `continue` 相同的行為（這是回歸逐筆相同的前提）。
  - 成交量單位換算（股 → 張）在 API 內用 `StockUtils` 完成，策略不再自行 `/ Units.LOT`。
  - `get_close_map()` 順帶解掉一個效能問題：`_1.py` 目前每個交易日對每檔股票各建一次 mask，改為一次建 dict 後 O(1) 查表。
- **產出**：`core/api/stock_price_api.py`、`tests/test_stock_price_api.py`。
- **驗證方式**：新增單元測試（建 in-memory SQLite 灌入固定樣本），涵蓋「查得到」「查不到」「價格為 0」三種情況。
- **相依**：S2。

## S4. `StockChipAPI` 新增具名查詢方法 ⬜

- **產出**：`core/api/stock_chip_api.py`、`tests/test_stock_chip_api.py`。
- **驗證方式**：同 S3。
- **相依**：S2。

## S5. 六支策略改打新 API ⬜

- **目的**：完成抽象洩漏的收口，這是本份工作唯一會動到回歸線的步驟。
- **做法**：**逐支改、逐支跑回歸**，不要一次全改。建議順序（由簡到繁）：`_1` → `_2` → `_4` → `_3` → `_5` → `overnight_lead_event_strategy`。
  - 只替換資料取用，**不動任何門檻、比較符號或迴圈結構**。
  - `overnight_lead_event_strategy.py` 另有 `yfinance` 的美股欄位（`"Close"`、`"TSM"`），**不在本份範圍**——那是第三方 API 的 schema，不是本專案資料庫；僅處理其第 120 行的 `"收盤價"`。
- **產出**：`core/strategies/stock/momentum_strategy_1.py` ~ `_5.py`、`core/strategies/stock/overnight_lead_event_strategy.py`。
- **驗證方式**：**每改一支就跑一次** `test_long_regression_snapshot`（915 筆 × 13 欄逐筆相同，約 54 秒，需 `stock.db`）。任一支破線即停止並在本節記錄中斷點。
- **相依**：S3、S4。

## S6. 防護測試 ⬜

- **目的**：讓「策略層又出現中文欄位字面值」在 CI 就被擋下，而不是等到換資料源才爆。
- **做法**：新增 `tests/test_strategy_data_access.py`，掃描 `core/strategies/` 下所有 `.py` 原始碼，斷言不含 `PriceColumn` / `ChipColumn` 的任一 value 字面值。實作用 `Path.read_text()` ＋ 字串比對即可，不需要 AST。
  - 例外清單留空；若日後真有必要保留，須在測試中明列檔案並註明理由。
- **產出**：`tests/test_strategy_data_access.py`。
- **驗證方式**：故意在某支策略塞回 `"收盤價"`，測試應失敗。
- **相依**：S5。若 [專案工程基建補齊.md](專案工程基建補齊.md) 的 CI 已就緒，此測試會自動納入。
