# 回測引擎多市場抽象（單一引擎 ＋ 可插拔 model）

## Abstract

- **背景／問題**：`core/backtest/backtester.py`（838 行）是純台股實作——`StockAccount`、`StockPositionManager`、`StockCostModel`、五支 `Stock*API`、`StockQuoteAdapter` 全部在 `__init__` 內直接 new 出來，`stock_id` 貫穿五個 model 與所有 log 字串，漲跌停與檔位規則寫死在 `validate_fill_price()`。既有規劃（[台期貨ETL與回測架構規劃.md](台期貨ETL與回測架構規劃.md) Phase1-6）是「平行複製一支 `FuturesBacktester`」，但那會複製掉其中約 4 成真正市場無關的骨架，兩邊永久漂移。
- **目標**：把引擎收斂為**單一 `Backtester`**，市場差異全部下沉為可插拔的 model（`InstrumentSpec` / `FillModel` / `CostModel` / `SettlementModel` / `DataFeed`），對齊 Backtrader `Cerebro`、Zipline `run_algorithm`、QuantConnect Lean `Engine`、Nautilus `BacktestEngine` 的一致做法：**引擎唯一，行為注入**。同時完成 `core/` 的解耦收尾（領域模組移出 `utils/`、`BasePositionManager` 抽取、死碼清除）。
- **範圍界線**：**行為必須零改變**——只搬移程式碼與抽取介面，不改任何費用公式、不改記帳口徑、不改報表輸出欄位名。**不做**：期貨／美股的 model 實作與 ETL（屬 [台期貨ETL與回測架構規劃.md](台期貨ETL與回測架構規劃.md)、[美股ETL與回測架構規劃.md](美股ETL與回測架構規劃.md)）、事件驅動 order queue 與 T+1 延遲成交、per-instrument 粒度的 model 掛載（見 §四）、`--mode live` 實盤路徑。
- **驗收標準**：每一步驟完成後，`test_long_regression_snapshot`（915 筆 × 13 欄）與新增的 SHORT 端到端快照皆逐筆相同，且 `tests/` 全數通過；`Backtester` 內不再 import 任何 `Stock*` 具體類別；新增一個市場所需的既有檔案改動為 **0 行**。

> **完成後的判準**：`grep -c "Stock" core/backtest/backtester.py` 應為 0。

## 一、為什麼不是「平行複製 FuturesBacktester」

把現有 838 行逐段分類的結果：

| 性質 | 內容 | 佔比 |
|------|------|------|
| **市場無關**（複製會浪費、且會漂移） | `run()` 日期迴圈、`execute_bar()` 執行順序、`validate_orders()` 方向白名單、`resolve_open/close_action()`、`execute_open/close_signal()`、`snapshot_daily_equity()` 骨架、`event_counts`、`generate_backtest_report()` | 約 4 成 |
| **市場規則**（介面共用、實作不同） | `validate_fill_price()`、`get_price_range()`、`check_stock_market_open()` | 約 2 成 |
| **台股信用交易專屬** | `build_cost_config()`、`enrich_orders()`、`enforce_day_trade_cover()`、`convert_to_margin_position()`、`accrue_holding_cost()`、`check_margin_call()` | 約 4 成 |

第三類看似「非分家不可」，但逐一檢查後**全部都能對應到 model 掛點**，沒有一項需要靠繼承分支：

| 現有方法（`backtester.py` 行號） | 下沉到 | 業界對應（Lean） |
|------|--------|------|
| `validate_fill_price` / `get_price_range`（257、307） | `FillModel` | `FillModel` |
| `build_cost_config` / `enrich_orders`（133、243） | `CostModel` ＋ `InstrumentSpec` | `FeeModel` ＋ `SymbolProperties` |
| `check_margin_call`（688） | `SettlementModel` | `BuyingPowerModel` / `MarginCallModel` |
| `accrue_holding_cost`（662） | `SettlementModel` | `MarginInterestRateModel` |
| `enforce_day_trade_cover` / `convert_to_margin_position`（522、595） | `SettlementModel` | `SettlementModel` |
| `snapshot_daily_equity` 的 `convert_lot_to_share`（794） | `InstrumentSpec.multiplier` | `SymbolProperties.ContractMultiplier` |

**關鍵洞察**：台股的「當沖日終強制回補」與期貨的「每日結算」，在架構上是**同一個掛點的兩種實作**——「一根 bar 收盤後，市場規則強制對部位做的事」。看出這點之後，切兩個引擎就沒有理由了。

## 二、目標架構

```
Backtester                      ← 唯一引擎，市場無關，無子類
  ├─ InstrumentSpec             ← 乘數、tick size、漲跌停規則、報價單位換算
  ├─ FillModel                  ← 成交價可信度（前視偏誤與不可能成交的擋板）
  ├─ CostModel                  ← 手續費／稅／借券費（期貨為期交稅）
  ├─ SettlementModel            ← 每根 bar 收盤後的強制動作
  └─ DataFeed                   ← 資料載入、報價轉換、交易日判定
```

引擎的建構子從「自己 new 具體類別」改為「收 model」：

```python
class Backtester:
    def __init__(
        self,
        strategy: BaseStrategy,
        instrument: InstrumentSpec,
        fill_model: BaseFillModel,
        cost_model: BaseCostModel,
        settlement: BaseSettlementModel,
        data_feed: BaseDataFeed,
    ) -> None:
```

`execute_bar()` 收斂為市場無關的流程：

```python
def execute_bar(self, date: datetime.date, quotes: List[BaseQuote]) -> None:
    if self.get_execution_order() == BarExecutionOrder.OPEN_THEN_CLOSE:
        self.execute_open_signal(quotes)
        self.execute_close_signal(quotes)
    else:
        self.execute_close_signal(quotes)
        self.execute_open_signal(quotes)

    # 台股：當沖強制回補 ＋ 借券費計提 ＋ 維持率追繳
    # 期貨：每日結算 ＋ 保證金追繳 ＋ 到期換月
    self.settlement.on_bar_close(date, quotes, self.account, self.event_counts)

    self.snapshot_daily_equity(date, quotes)
```

**方向（LONG／SHORT）與市場（股票／期貨）是兩條獨立的軸**，本次只動「市場」那條。`validate_orders()`、`resolve_open_action()`、`resolve_close_action()` 本來就與市場無關（期貨的多空語意與股票相同），一律留在引擎內不動。[放空回測框架規格](../docs/backtest/short-selling-framework.md) §1 原則 2「方向來自訂單，策略只做白名單」是本次重構的**基礎**，不是被取代的對象。

## 三、為什麼先做 3+2 個 model 而不是 Lean 的五件套

Lean 把 `FeeModel` / `FillModel` / `BuyingPowerModel` / `MarginCallModel` / `SettlementModel` / `SlippageModel` 拆得很細，是因為它要支撐十幾種資產類別與多家券商。本專案只有兩個市場，**先合成 `SettlementModel` 一個**（吸收保證金與追繳），等期貨的原始／維持保證金真的塞不進去再拆第四個。少即是多。

`DataFeed` 與 `InstrumentSpec` 不算「行為 model」，但必須一起抽，否則 `Backtester.load_datasets()` 仍會 import 五支 `Stock*API`，`grep -c "Stock" == 0` 的驗收標準過不了。

## 四、已知簡化（明確不做，但要記錄）

| 項目 | 影響 | 為何不做 |
|------|------|----------|
| **per-instrument 粒度的 model 掛載** | 無法在同一次回測同時持有台股與台指期（跨市場組合／避險） | 業界（Lean 掛在 `Security`、Nautilus 掛在 `Instrument`）確實是這個粒度，本次採 per-run 簡化。[台期貨ETL與回測架構規劃.md](台期貨ETL與回測架構規劃.md) 的範圍界線本來就寫明「不含跨市場組合回測」。升級路徑乾淨：把 model 從 `Backtester` 移到 `InstrumentSpec` 物件上，引擎迴圈不動 |
| 事件驅動 order queue（T+1 延遲成交、限價單未成交、部分成交） | 追繳仍只能以觸發當日收盤價回補 | 本質是引擎典範轉移，非本次範圍。既有紀錄見 [放空回測框架規格](../docs/backtest/short-selling-framework.md) §7.2 與 [回測引擎當沖執行順序重構.md](回測引擎當沖執行順序重構.md) S4 |

## 六、Model 層是否改用 `@dataclass`（2026-08-07 評估）

`core/models/stock/*.py` 全部是手寫 `__init__` 逐欄位賦值的 plain class。Phase1-1 本來就要重寫這些檔案（加 `symbol` 欄位、抽 `core/models/base/`），是唯一邊際成本趨近於零的施作時機，因此在此記錄評估結果，避免日後重複討論。

| 選項 | 評估 |
|------|------|
| **pydantic**（專案已裝 2.12.3） | **否決**。回測逐日逐檔建立 `StockQuote`，約 1800 檔 × 1250 交易日 ＝ 百萬量級的物件建立，全部落在 hot path。pydantic v2 再快也是每次都跑驗證，屬純開銷；且 model 的資料來源是自家 ETL，不是外部輸入，驗證的效益本來就低 |
| **`@dataclass`**（stdlib） | **可考慮**。只生成 `__init__`，零執行期成本、零新相依；可省下數百行樣板，並免費得到 `__eq__` / `__repr__`（測試斷言與快照比對會好寫很多） |
| **維持現狀** | **預設選項**。`CLAUDE.md` §1.4「既有風格優先」；且 `StockPosition` / `StockTradeRecord` 被 `reporter.py`、`analyzer.py` 直接讀屬性，改寫會拿回歸線換可讀性 |

**結論**：不為此另開 backlog。若 Phase1-1 施作時判斷改動範圍可控，可在該步驟內一次改為 `@dataclass`；否則維持現狀。**無論選哪一項，都不得單獨為此開一次回歸驗證。**

> **決定（2026-08-07，Phase1-1 施作時）：維持現狀，不改 `@dataclass`。**
>
> 施作後多出一個當時未預見、且具決定性的技術理由：本步驟的相容策略是「`Stock*` 的 `__init__` 收 `stock_id`，對映到 base 的 `symbol` 欄位」——**參數名與欄位名刻意不同**。`@dataclass` 是由欄位名生成 `__init__` 參數名的，要維持這個對映就得自己寫 `__init__`，等於放棄 `@dataclass` 的唯一好處。若改為讓參數名跟著欄位改成 `symbol`，則 6 支策略與全部測試的 `StockQuote(stock_id=...)` 呼叫端全數要改，與「策略層零改動」的前提直接衝突。
>
> 次要理由：`@dataclass` 預設生成的 `__eq__` 會把 model 的相等語意從「同一個物件」改為「所有欄位相同」，而 `positions` / `trade_records` 是 list 容器，此變更屬於行為改變，違反本文件 Phase 1 的紅線。
>
> **此議題到此結案，後續步驟不需再評估。**

`run_mix_backtest()` 是 `pass`（`backtester.py:412`），但 `Scale.MIX` 並非單純的未實作分支——它已經散進策略的 `setup_apis()` 分支判斷，並在其中製造了**永遠不會命中的條件**（`momentum_strategy_1.py:70-78`、`_4.py:66-74`、`_5.py:77-85` 三支同構）：

```python
if self.scale in (Scale.TICK, Scale.MIX):      # MIX 在此被攔截
    ...
elif self.scale in (Scale.DAY, Scale.MIX):     # MIX 不可能走到
    ...
elif self.scale in (Scale.MIX, Scale.ALL):     # MIX 不可能走到；但 ALL 走得到
    ...
```

**精確的說法**：不可達的是第二、三個分支裡的 `Scale.MIX` 條件，**不是整個 `elif`**——`Scale.ALL` 仍會正常命中第三個分支（前兩個分支都不含 `ALL`）。因此若採做法 A，只能移除三個分支中的 `Scale.MIX`，**不可整段刪掉第三個 `elif`**，否則 `Scale.ALL` 會失去「tick ＋ 日 K 同時載入」的既有行為。

Phase2-6 引擎瘦身時**必須就此做出決定**，二選一：

- **做法 A（建議）**：從 `Scale` enum 移除 `MIX`，刪除 `run_mix_backtest()` 與各策略的相關分支。理由：`Scale.ALL` 已存在且語意重疊，而混合級別回測沒有任何策略在用，屬於「宣告了但從未成形」的設計。
- **做法 B**：保留並實作。此時需先定義清楚「同一根 bar 內 Tick 與日 K 的先後語意」，而這與 [回測引擎當沖執行順序重構.md](回測引擎當沖執行順序重構.md) 的 bar policy 直接相關，應併入該份討論。

無論選哪個，Phase2-7 改寫 `setup_apis()` 時**都不要把不可達的 `elif` 一起搬過去**。

## 拆分原則與中斷處理

- 每個步驟都是**可獨立 commit、可獨立驗證**的最小單位，驗收一律是「回歸雙線 ＋ 全測試」。
- **Phase 1 與 Phase 2 的所有步驟都必須行為零改變**。任何一步若發現「不改行為就搬不動」，代表該處藏有設計問題——**停下來記中斷點、另開 backlog，不要順手改公式**。這是本次重構唯一的紅線。
- 中斷時依 [`manage-backlog` skill §3](../.claude/skills/manage-backlog/SKILL.md#3-實作過程的狀態更新) 在該步驟章節末尾補「⛔ 中斷紀錄」，寫明已完成／未完成／原因／恢復下一步。
