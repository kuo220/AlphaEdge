# 放空（SHORT）回測框架建置

> 用途:`core/backtest` 目前的放空（`PositionType.SHORT`）路徑是**未完成的半成品**——資料模型已經預留欄位,但開平倉記帳、損益計算、成本模型完全沒寫。本文件盤點整條路徑（`run.py` → `Backtester` → `StockPositionManager` → `StockUtils` → `StockAccount`）需要補的地方,做成**通用框架**,而不是綁死在單一策略上,之後任何放空策略都可以直接用。
>
> 觸發需求:[放空策略_外資大賣強勢股當沖.md](放空策略_外資大賣強勢股當沖.md) 是第一個會用到這個框架的策略,但框架本身應獨立完成、獨立驗證。

---

## 一、現況缺口（已在程式碼中確認）

### 1.1 `core/managers/stock/position/position_manager.py`——核心缺口

- `open_position()`（79–86 行）:`PositionType.SHORT + Action.SELL` 分支**只有 `logger.info`**,沒有：
  - 計算開倉價值、手續費、（放空特有的）稅務。
  - 建立 `StockPosition` 物件並塞進 `account.positions`。
  - 更新 `account.balance`。
  - 函式最終回傳的 `position` 仍是 `None`,呼叫端 `Backtester.execute_open_signal`（`core/backtest/backtester.py`）拿到 `None` 就直接跳過,策略等於下單失敗但沒有任何錯誤訊息。
- `close_position()`（195–202 行）:`PositionType.SHORT + Action.BUY`（回補）分支**只有 `logger.info` + `pass`**,沒有：
  - 計算損益（方向與 LONG 相反：`realized_pnl = (賣出價 − 買進價) × 股數`，因為是先賣後買）。
  - 更新 `position.volume`、`is_closed`、`account.balance`、`account.realized_pnl`。
  - 產生 `StockTradeRecord`。
  - 目前這段甚至不會被回測發現有錯——不會 raise、不會 log warning,回測會「安靜地」讓放空單消失。

### 1.2 `core/utils/instrument.py`（`StockUtils`）——成本與損益公式只支援 LONG

- `calculate_transaction_commission` / `calculate_transaction_tax` / `calculate_net_profit` / `calculate_roi` 的 docstring 全部明講「For long position」。
- `Commission`（`core/utils/constant.py` 82–88 行）只有單一 `TaxRate = 0.003`,**沒有當沖證交稅減半的稅率常數**,也沒有跨日融券的保證金／借券費常數。
- 目前完全沒有依 `PositionType` 或「是否當沖」切換稅率／損益公式的機制。

### 1.3 `core/backtest/backtester.py`——執行順序與同日先賣後買互斥

- `run_day_backtest` 固定 `execute_close_signal()` → `execute_open_signal()`（先平倉再開倉),這代表**同一天**內先開的 SHORT 倉不可能在同一天被平倉——平倉判斷用的是「呼叫當下 `account.positions` 裡已存在的部位」,而新開的部位要等到**下一次呼叫**（也就是下一個交易日）才會被 `execute_close_signal` 看到。
- 這正是 [回測引擎當沖執行順序重構.md](回測引擎當沖執行順序重構.md) 已經記錄的問題,**是本框架的前置依賴,不是本文件要重做的範圍**——本文件只指出「先賣後買當沖類放空策略」一定會撞到這個限制,實作順序上必須等（或搭配）那份重構完成。
- `execute_close_signal` / `execute_open_signal` 用 `self.account.check_has_position(stock_id)` 判斷持倉,而 `check_has_position` **不分方向**(只看 `stock_id`)——如果未來同一檔股票同時有 LONG 和 SHORT 倉位（例如避險策略),目前的持倉查詢與平倉邏輯會混在一起,需要在框架設計時決定是否允許同標的雙向持倉,或直接限制「同一標的同時間只能有一種方向」。

### 1.4 `core/backtest/analysis/analyzer.py`、`core/backtest/report/reporter.py`——目前是方向無關的,不用大改

- 兩者的統計（勝率、獲利因子、Sharpe 等）都是直接用 `record.realized_pnl` / `record.roi` 加總,**不依賴 `position_type`**,只要 `StockTradeRecord` 的 `realized_pnl`／`roi` 算對,報表與分析層基本不用改。`reporter.py` 285 行有輸出 `record.position_type.value`,已經是通用的。

### 1.5 資料模型層——欄位已經夠用,不用改 schema

- `StockPosition`、`StockOrder`、`StockTradeRecord` 都已經有 `position_type: PositionType`（`LONG`/`SHORT`）欄位,`PositionType`、`Action` 這兩個 enum（`core/utils/constant.py` 32–37、107–112 行）也都已經有 `SHORT`/`BUY`/`SELL`。**這層不缺欄位,缺的是邏輯**。

## 二、設計範圍與定位

先鎖定**當沖型放空（先賣後買,同日結清)**為第一階段目標,理由：

- 不涉及過夜保證金／利息計算,成本模型單純很多。
- 是目前有明確策略需求（外資大賣策略）的實際用例。
- 跨日融券（留倉）可以在此框架穩定後再擴充,屬於「同一套骨架、換一組成本參數」的延伸,不需要重新設計。

**本階段不做**:融券保證金追繳、借券費率、券源可得性檢查（是否借得到券）、平盤下放空限制的個股狀態判斷。這些留給跨日放空需求出現時再開新 backlog。

## 三、需要實作的變更（依檔案列出）

### 3.1 `core/utils/constant.py`

- 在 `Commission` 旁新增當沖相關常數,例如 `DayTradeTaxRate`（現股當沖證交稅減半率,實作時查核現行是否仍展延、到期日為何,不要寫死成永久有效）。
- 是否新增 `PositionType` 相關的手續費/稅務差異開關,視 §3.2 的函式簽章設計決定（例如改成吃 `position_type` + `is_day_trade` 參數,而非另開一組常數）。

### 3.2 `core/utils/instrument.py`(`StockUtils`)

- `calculate_transaction_tax` 需能依「是否為當沖賣出」套用減半稅率——簽章可能改為 `calculate_transaction_tax(price, volume, is_day_trade: bool = False)`。
- 新增（或擴充既有）損益計算,支援 SHORT 方向：
  - `calculate_net_profit` / `calculate_roi` 目前假設「先買後賣」,SHORT 是「先賣後買」,買賣價代入順序相反,需要明確參數命名（例如統一用 `entry_price`/`exit_price` 取代 `buy_price`/`sell_price`,避免呼叫端搞混方向)，或是新增 `calculate_short_net_profit` 之類的對應函式。
  - 手續費計算（`calculate_transaction_commission`）本身方向無關（買賣手續費率相同),不用改,但呼叫端要注意「開倉是賣出、平倉是買進」的手續費各自獨立計算,不能套用 LONG 版本「買進手續費 + 賣出手續費」的變數命名去理解。

### 3.3 `core/managers/stock/position/position_manager.py`

- `open_position()` 補 `SHORT + SELL` 分支：
  1. 計算開倉（賣出）手續費 + 是否課當沖稅（視 `StockOrder`／策略設定是否標記為當沖)。
  2. 建立 `StockPosition(position_type=PositionType.SHORT, ...)`。
  3. 資金處理方式需明確定義並寫進 docstring：建議做法是「賣出所得**不**立即計入可用餘額,先記在部位裡,等回補平倉時才一次結算損益到 `account.balance`」,避免當沖策略在同一天內把放空賣出所得誤用去開別的倉位（除非你們刻意允許,那也要顯式寫清楚並在文件標註）。
  4. 資金/風控檢查:目前 LONG 分支用 `account.balance >= position_value + open_cost` 檔開倉,SHORT 因為沒有真的付出本金,需要另外定義檢查條件（例如：限制單一部位曝險上限、或先不做資金檢查、僅做部位數上限檢查，需要在文件與程式註解中寫明這是「簡化版,不模擬保證金」）。
- `close_position()` 補 `SHORT + BUY`（回補）分支：
  1. 依 §3.2 的損益公式算 `realized_pnl`（賣出價 − 買進價,乘股數,扣手續費/稅)。
  2. 更新 `position.volume`、`is_closed`、`account.balance`、`account.realized_pnl`。
  3. 產生 `StockTradeRecord(position_type=PositionType.SHORT, buy_date=<回補日>, buy_price=<回補價>, sell_date=<開倉日>, sell_price=<開倉價>, ...)`——**要決定 `buy_date`/`sell_date` 在 SHORT 情境下的語意**（是「操作動作」還是「時間先後」),目前欄位命名是以 LONG 的時間順序（先買後賣）設計,SHORT 情境下建議仍以「動作」對應（`sell_*` = 放空開倉那筆、`buy_*` = 回補那筆),並在 `StockTradeRecord` 的 docstring 補充說明,避免之後有人誤讀報表。
  4. 依 FIFO 邏輯比照 LONG 分支處理部分平倉（現有 LONG 分支已支援部分平倉拆單,SHORT 應維持一致的行為）。

### 3.4 `core/backtest/backtester.py`

- 本身不需要新增放空專屬方法,但：
  - 需確認 `execute_open_signal` / `execute_close_signal` 在 `position` 為 `None`（例如資金不足被拒絕開倉）時的行為對 SHORT 也適用（目前邏輯是通用的,理論上補完 §3.3 後就會自然生效)。
  - 若要支援「T 日開盤放空、T 日尾盤回補」,**必須**先完成或至少局部套用 [回測引擎當沖執行順序重構.md](回測引擎當沖執行順序重構.md) 的 `BarExecutionOrder`（至少要有 `OPEN_THEN_CLOSE` 或等效機制),否則同日開平倉在現有引擎下永遠不會發生。

### 3.5 `core/strategies/stock/base.py` / `core/strategies/README.md`

- `enable_intraday`、`position_type` 欄位已存在,不需新增欄位。
- 需要在 `README.md` 補一段「如何寫放空策略」的說明（`check_open_signal` 回傳 `Action.SELL + PositionType.SHORT`、`check_close_signal` 回傳 `Action.BUY + PositionType.SHORT`),等框架完成後一併更新,避免文件與程式落差（`core/strategies/README.md` 目前的範例全是 LONG）。

### 3.6 `run.py`

- 不需要改動。`run.py` 只負責載入策略類別與呼叫 `Backtester`,放空與否是策略內部（`check_open_signal`/`check_close_signal` 回傳什麼 `PositionType`）與 `Backtester`/`PositionManager` 的事,入口層不感知方向。

## 四、與其他 backlog 項目的關係

- **前置依賴**:[回測引擎當沖執行順序重構.md](回測引擎當沖執行順序重構.md)——若目標是「同日開平倉」的放空策略,這份要先做（或至少做到 P0）。若只是要先支援**跨日**放空（開倉後隔天以後才回補),則不受這個限制,可以先獨立完成本框架。
- **並行可協調**:[回測滑價與執行係數.md](回測滑價與執行係數.md)——放空的開平倉價位一樣會經過滑價調整,兩邊都會碰 `execute_open_signal`/`execute_close_signal` 的調價掛點,實作時注意順序（建議：先滑價調整成交價,再用調整後價格算手續費/稅,SHORT 與 LONG 一致處理,不需要另外分流)。
- **後續應用**:[放空策略_外資大賣強勢股當沖.md](放空策略_外資大賣強勢股當沖.md)——本框架完成後的第一個驗證用例。

## 五、驗收建議

1. **單元/範例驗證**:寫一組最小案例（例如:100 元放空 1 張,90 元回補),手算應得損益與手續費,對照 `calculate_short_net_profit`（或等效函式）與 `close_position` 產生的 `StockTradeRecord` 數字一致。
2. **回歸不影響 LONG**:完成後跑一個既有的 LONG 策略（例如 `MomentumStrategy1`),確認結果與改動前一致（LONG 路徑不應被動到）。
3. **同日開平倉的邊界情況**:若 §3.4 的執行順序尚未解決,應該讓「同日開平倉」在測試中**明確失敗或給出警告**,而不是安靜地不成交——避免使用者誤以為策略跑成功但其實一張單都沒下。
4. **部分平倉**:比照 LONG 分支的 FIFO 拆單邏輯,測試「開兩筆 SHORT、只回補其中一部分」的情境,確認 `position.volume`、`is_closed`、帳戶餘額都正確。
