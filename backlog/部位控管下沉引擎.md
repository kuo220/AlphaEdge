# 部位控管下沉引擎

## Abstract

- **背景／問題**：`max_holdings`（最大持倉檔數）宣告在 `core/strategies/stock/base.py:37`，`Backtester` 也在 `backtester.py:77` 讀進 `self.max_holdings`——**但引擎從頭到尾沒有使用它**。實際的檔數上限與資金切分，是由每一支策略在自己的 `calculate_position_size()` 內各寫一遍（`momentum_strategy_1.py:157-187`、`_2.py:166-200`、`_4.py:201`、`_5.py:304-333`），四份程式碼結構幾乎相同卻已經開始漂移。
- **目標**：把「檔數上限 ＋ 等權資金切分 ＋ 張數換算」抽成可重用的 `PositionSizer`，並讓 `max_holdings` 成為**引擎側的硬上限**——策略不呼叫 sizer 也不能突破。策略的 `calculate_position_size()` 回歸其本職：決定用什麼價格、選哪些標的。
- **範圍界線**：**行為必須零改變**——`PositionSizer` 的預設實作要逐行對齊現行等權切分公式（含 `int()` 無條件捨去與「至少 1 張」的門檻）。**不做**：波動度加權／Kelly／風險平價等新的部位配置演算法、不做單檔曝險上限（放空側的 `max_short_exposure_ratio` 已在 `StockCostModel` 內，不重複實作）、不改任何策略的進出場條件。
- **驗收標準**：`test_long_regression_snapshot`（915 筆 × 13 欄）逐筆相同；四支策略的 `calculate_position_size()` 內不再出現 `available_position_cnt` 與 `per_position_size` 的重複計算；新增的引擎側上限測試能擋下「策略回傳超過 `max_holdings` 的開倉單」。

## 現況差異

四支策略的開倉 sizing 邏輯對照（撰寫本文件時，2026-08-07）：

| 項目 | `_1.py` | `_2.py` | `_4.py` | `_5.py` |
|------|:-------:|:-------:|:-------:|:-------:|
| 檔數上限計算 | `max(0, max_holdings - 持倉數)` | 同左 | 同左 | 同左 |
| **`max_holdings is None` 時** | `len(stock_quotes)` | **`0`（完全不開倉）** | `len(stock_quotes)` | `len(stock_quotes)` |
| 每檔資金 | `balance / 可開檔數` | 同左 | 同左 | 同左 |
| 下單參考價 | `stock_quote.close` | `tick_quote.close` | `open` | `open` |
| 價格有效性檢查 | 無 | `price <= 0` 跳過 | 有 | `open_px <= 0` 跳過 |
| 張數 | `int(每檔資金 / (價 × Units.LOT))` | 同左 | 同左 | 同左 |
| 最低張數門檻 | `>= 1` | 同左 | 同左 | 同左 |

**兩個要在 S1 定案的問題**：

1. **`max_holdings is None` 的語意不一致**：`_2.py:166-171` 走 `else: available_position_cnt = 0`，語意是「沒設上限 ⇒ 不開倉」；其他三支是「沒設上限 ⇒ 不限制」。兩者恰好相反。實務上四支策略都在 `__init__` 明確設了 `max_holdings`，所以這條分支目前跑不到——**但這正是重複程式碼漂移的證據**，統一時須明確選一種語意並寫入 docstring。建議取「`None` ⇒ 不限制」（多數派，且與欄位型別 `Optional[int]` 的直覺一致）。
2. **下單參考價不屬於 sizing 的職責**：四支各用 `close`／`tick_quote.close`／`open`，這是**策略決策**，不該進 `PositionSizer`。S2 的介面設計要讓價格由呼叫端傳入。

> `momentum_strategy_3.py` 與 `overnight_lead_event_strategy.py` 的 sizing 樣態不同（前者非等權、後者 `max_holdings = 1`），**本份範圍不動它們**；S2 的介面若涵蓋不到就維持原狀，不要為了統一而扭曲。

| 落點 | 優點 | 缺點 |

## S1. 盤點差異並定案基準公式 ⬜

- **目的**：四份實作已經漂移，抽取前必須先確定「哪一份是基準」，否則回歸一定破線。
- **做法**：
  1. 以 §現況差異 的表格為準，逐行核對四支策略的 `calculate_position_size()`。
  2. 定案基準公式（建議取 `_1.py` 的版本，它是其他三支的來源）：
     ```
     可開檔數 = max(0, max_holdings - 現有持倉檔數)   # max_holdings 為 None 時不限制
     每檔資金 = account.balance / 可開檔數
     張數     = int(每檔資金 / (參考價 × Units.LOT))   # 無條件捨去
     下單條件 = 張數 >= 1
     每下一單，可開檔數 -= 1；歸零即停止
     ```
  3. 定案 `max_holdings is None` 的語意，並寫進 `BaseStockStrategy` 的欄位註解。
- **產出**：本文件本節補上決策段落；`core/strategies/stock/base.py:37` 的欄位註解。
- **驗證方式**：人工逐行核對；差異表無遺漏項。
- **相依**：無。

## S2. 抽出 `PositionSizer` ⬜

- **目的**：讓等權切分只存在一份實作，並可獨立測試（純記憶體、不連 DB）。
- **做法**：新增 `core/backtest/sizing.py`，介面設計讓**參考價由呼叫端決定**：

  ```python
  class EqualWeightSizer:
      """等權資金切分：可開檔數均分餘額，逐檔換算張數（無條件捨去，至少 1 張）"""

      def size(
          self,
          account: StockAccount,
          candidates: List[Tuple[StockQuote, float]],  # (報價, 該策略選定的參考價)
          max_holdings: Optional[int],
      ) -> List[Tuple[StockQuote, float, int]]:       # (報價, 參考價, 張數)
  ```

  - 回傳**張數**而非 `StockOrder`：`position_type`、`action`、`date` 仍由策略組裝，避免 sizer 越權決定方向。
  - 參考價 `<= 0` 一律跳過（吸收 `_2.py`／`_5.py` 已有的檢查，補上 `_1.py` 缺的那一項——**這是唯一允許的行為變更**，且只在資料異常時才會觸發，須在 S3 的回歸中確認 915 筆不受影響）。
  - 預留 `BasePositionSizer` ABC，日後要加波動度加權時直接新增實作，不改呼叫端。
- **產出**：`core/backtest/sizing.py`、`tests/backtest/test_position_sizer.py`。
- **驗證方式**：單元測試涵蓋——上限為 `None`、上限已滿（可開檔數 0）、餘額不足 1 張、候選數多於可開檔數、參考價為 0 共 5 種情況。
- **相依**：S1。

## S3. 四支策略改用 `PositionSizer` ⬜

- **目的**：消除四份重複實作，這是本份唯一會動到回歸線的步驟。
- **做法**：**逐支改、逐支跑回歸**，順序 `_1` → `_4` → `_5` → `_2`（`_2` 是 Tick 級別且 `None` 語意要翻轉，風險最高，放最後）。
  - 策略只保留：篩選候選標的、決定參考價、把 sizer 回傳的張數組成 `StockOrder`。
  - `SELL`（平倉）分支**不動**——那是「照持倉張數全平」，與資金配置無關。
- **產出**：`core/strategies/stock/momentum_strategy_{1,2,4,5}.py`。
- **驗證方式**：每改一支跑一次 `test_long_regression_snapshot`（915 筆逐筆相同）。破線即停止並在本節記錄中斷點。
- **相依**：S2。

## S4. 引擎側 `max_holdings` 硬上限 ⬜

- **目的**：讓 `max_holdings` 成為真正的風控，而不是「策略願意遵守才生效」的建議值。現況下一支新策略只要沒呼叫 sizer，就能無限開倉且不會有任何警告。
- **做法**：於 `core/backtest/backtester.py` 的 `execute_open_signal()`，在 `validate_orders()` 之後、`position_manager.open_position()` 之前加入截斷：
  - 計算 `剩餘名額 = max_holdings - account.get_position_count()`，超額的開倉單一律剔除。
  - 沿用既有的**顯式計數**慣例（`backtester.py:95-102`），新增 `event_counts["rejected_max_holdings"]`，並以 `logger.warning` 記錄被剔除的標的——**禁止靜默丟棄**。
  - `max_holdings` 為 `None` 時不做任何截斷（依 S1 定案語意）。
- **產出**：`core/backtest/backtester.py`、`core/backtest/report/reporter.py`（`generate_event_report` 的事件清單需納入新 key）、`tests/backtest/test_backtester_max_holdings.py`。
- **驗證方式**：
  1. 新增測試：用 `conftest.py` 的 `ScriptedStrategy` 故意回傳超過上限的開倉單，斷言超額部分被剔除且計數 +1。
  2. LONG 回歸 915 筆逐筆相同（既有策略本來就自我約束，此截斷不應觸發——**若回歸破線，代表現有策略其實有超額開倉，屬於實錯，須先查明再繼續**）。
- **相依**：S3。

- **產出**：`core/backtest/README.md`、`.claude/skills/develop-strategy/SKILL.md`。
- **驗證方式**：人工檢視；照文件敘述能寫出一支不含 `available_position_cnt` 的新策略。
- **相依**：S4。
