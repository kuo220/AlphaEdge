# 爬蟲入庫時序與中斷風險改善

## Abstract（摘要）

- **背景／問題**：2026-08-15 執行 `margin` 歷史回補時風險實際發生——`downloads/margin/` 已爬 3,790 個 CSV（2013-01-02 ～ 2020-10-13），程序中斷後 **DB `margin` 表仍為 0 列**。原因是多數 updater 採「整段日期範圍全部 crawl／clean 完，最後才一次 `add_to_db()`」的時序，且 resume 依「DB 表內最新日期」判斷起點：中斷則資料永遠不入庫、表空則從頭重爬（已下載的 CSV 不被 resume 認得）。全 updater 稽核後確認 price／chip／margin 同屬高風險，tick 另有重複入庫風險。
- **目標**：中斷不歸零——高風險 updater 的長時間回補中斷後，重跑能接續已完成的部分；已下載的 CSV 能獨立入庫。
- **範圍界線**：**不**重寫 pipeline 四層架構；**不**動 FinMind `broker_trading`（已是逐組合入庫＋metadata resume，模式正確）；**不**動 DolphinDB 的表 schema（`keepDuplicates=ALL` 是 tick 語意的刻意選擇，重複風險由入庫流程把關）；dividend／mrr／fs 量級小，僅順手受益、不特別施作。
- **驗收標準**：`margin` 表涵蓋 2013 起至近日（S1）；price／chip／margin 回補中途 kill 後重跑，不重爬已入庫的日期（S2）；重載同一批 CSV 不產生 PK 撞鍵噪音（S3）。

## 現況稽核（2026-08-15）

| `StockMarginUpdater` | 整段 crawl 完才一次 load（L90~123） | DB 最新 `date` +1 | 不入庫＋表空從頭重爬 | PK 撞鍵（有噪音） | **高** |

| `StockDividendUpdater` | 按年 crawl、最後 load | 同上 | 同上，但量級小（十餘年 × 2 來源） | `INSERT OR REPLACE`（冪等） | 低 |
| `MonthlyRevenueReportUpdater` | 年月迴圈後一次 load | DB 最大年月 +1 | 同上，約百餘個年月 | 先查既有鍵過濾 | 中 |
| `FinancialStatementUpdater` | 每種報表全季 crawl 完才 load | 各表最大年季 +1 | 同上 | PK 撞鍵（有噪音） | 中 |
| `StockTickUpdater` | 全部 crawl/clean 完才一次 load 到 DolphinDB | 固定起日 ＋ `tick_metadata.json` | 見 S4 | **無**（`keepDuplicates=ALL`） | **高** |
| `FinMindUpdater`（broker_trading） | **逐組合入庫、每 50 組 commit** | metadata（與 DB 同步） | 已 commit 部分保留 | 查鍵過濾 | 低（模式正確） |

共通事實：crawler 回傳 DataFrame、由 cleaner 落地 CSV；`add_to_db(remove_files=False)` 預設保留 downloads，因此**中斷後可手動呼叫 loader 只做入庫**，但 updater 沒有提供「僅 load」的入口。

## 步驟詳述

### S1. margin 歷史回補：先入庫既有 CSV、再補完剩餘區間 ⬜

- **目的**：回補程序已中斷且 0 筆入庫，`check_borrowable=True` 的回測目前整場「查無資料 → 放行＋warning」，券源檢核（`放空回測市場約束補齊` S2 的成果）實際上仍未生效。
- **做法**：
  1. 手動呼叫 `StockMarginLoader.add_to_db()` 把既有 3,790 個 CSV（2013-01-02 ～ 2020-10-13）先入庫。
  2. 入庫後 `get_actual_update_start_date()` 即回傳 2020-10-14，重跑 `python -m tasks.update_db --target margin` 補完剩餘區間（約 5.8 年）。
  3. 若 S2 先完成，直接用改良後的流程跑剩餘區間。
- **產出**：DB `margin` 表資料。
- **驗證方式**：`SELECT COUNT(*), MIN(date), MAX(date) FROM margin` 涵蓋 2013-01-02 起至近日；抽樣數日與證交所／櫃買原站比對；跑一次 `check_borrowable=True` 的回測，不再出現整場「查無資料」warning。
- **相依**：無（S2 完成與否都能做，先做可立即解掉券源檢核的資料缺口）。

### S2. 高風險組改分批入庫 ⬜

- **目的**：price／chip／margin 的歷史回補動輒數千個交易日、數小時，「整段爬完才入庫」讓中斷成本等於全部重來。
- **做法**：在三個 updater 的日期迴圈中，改為**按月（或按年）批次呼叫 `add_to_db()`**——每批只入庫該批新產出的 CSV；批次大小取「單批失敗重爬可接受」為準。同時 resume 邏輯不用改（DB 最新日期會隨批次推進）。注意 `add_to_db()` 目前掃整個 downloads 目錄，分批時須支援「只載入指定檔案清單」或依日期過濾，避免每批重掃全目錄放大 S3 的撞鍵噪音。
- **產出**：`core/pipeline/updaters/stock_price_updater.py`、`stock_chip_updater.py`、`stock_margin_updater.py`，視需要含各自 loader。
- **驗證方式**：以暫存 DB 跑一段回補、中途 kill，重跑後已入庫日期不重爬；完整跑完的結果與舊流程逐筆相同。
- **相依**：建議與 S3 同批施作（分批入庫會放大重載場景）。

### S3. loader 重複入庫防護統一 ⬜

- **目的**：chip／margin／財報三處 loader 直接 `to_sql(if_exists="append")`，重載同一批 CSV 靠 PK 撞鍵擋下——資料不會重複，但整批 warning 噪音會淹沒真正的錯誤；price／mrr 已有「先查既有鍵再過濾」的正確做法，兩套並存。
- **做法**：把 `StockChipLoader`、`StockMarginLoader`、`FinancialStatementLoader` 的入庫改為比照 `StockPriceLoader`（先查既有鍵過濾後再 append），或改用 `INSERT OR IGNORE`。此即 `放空回測市場約束補齊` S1 完成紀錄中「沿用既有慣例的已知問題」那一條的正式處置。
- **產出**：`core/pipeline/loaders/stock_chip_loader.py`、`stock_margin_loader.py`、`financial_statement_loader.py`。
- **驗證方式**：對同一批 CSV 連續 `add_to_db()` 兩次，第二次無任何 warning 且列數不變。
- **相依**：無。

### S4. tick 入庫時序與重複列風險 ⬜

- **目的**：tick 的風險結構與 SQLite 組不同，單獨處理：
  1. `update_db --target tick` 的 `start_date` **固定**為 `TICK_UPDATE_START_DATE`（2024-05-10），不依 DB 推進；跳過已爬日期靠 `tick_metadata.json`。
  2. metadata 在 **load 完成後**才從 CSV 更新（updater L219~222）——load 前中斷則 metadata 落後，重跑會重爬並**覆寫** CSV。
  3. DolphinDB 建表 `keepDuplicates=ALL`（loader L137）：同一 CSV 重複 load 會產生重複 tick，**沒有 DB 層去重**。
- **做法**：（1）load 改為逐檔完成即更新該檔 metadata，或在 load 前記錄「待入庫清單」；（2）入庫前查 DolphinDB 該 `(stock_id, date)` 是否已有資料，已有則跳過該檔；（3）評估 `--target tick` 的起日改為「metadata 最新日」而非固定常數。
- **產出**：`core/pipeline/updaters/stock_tick_updater.py`、`core/pipeline/loaders/stock_tick_loader.py`、視需要 `tasks/update_db.py`。
- **驗證方式**：同一批 CSV 重複執行 load，DolphinDB 該日筆數不變；load 中途 kill 後重跑不產生重複列。
- **相依**：無（需 DolphinDB 環境才能驗證）。
