# Backlog 索引

本檔案彙整 `backlog/` 內**所有待辦事項文件**的優先級與完成狀態，作為單一入口。

- 新增待辦 `.md` 時：在下表新增一列。
- 實作進度變動時：同步更新該列的「狀態」與「進度」。
- 項目完成並整份移出 `backlog/`（見 [`manage-backlog` skill §5](../.claude/skills/manage-backlog/SKILL.md#5-完成後的處理)）時：刪除該列。

**狀態圖例**：⬜ 未開始（僅規劃）｜🔄 進行中｜✅ 完成｜⛔ 中斷（需在該文件註明中斷點與恢復下一步）｜⏸ 暫緩

> 文件結構與狀態標記規範見 [`manage-backlog` skill](../.claude/skills/manage-backlog/SKILL.md)。

**優先級**：`P0` 最高（阻塞其他項目或已在進行）→ `P3` 最低（長期架構規劃）。此處的 `P` 指 Priority；各文件內部的階段編號一律寫成 `Phase1-1`，不縮寫成 `P1-1`，避免與優先級混淆。

## 執行梯次（Critical Path）

**優先級回答「多重要」，梯次回答「什麼時候能動工」，兩者不同**——高優先級的工作可能因為前置未完成而不能先做。

梯次的排序依據**不是**重要性，而是「誰會讓 `test_long_regression_snapshot`（915 筆 × 13 欄）失效」。這條 baseline 是全 `backlog/` 的共用資產：部位控管、策略層欄位抽象、執行真實度，全部拿它當驗收條件。**會換掉 baseline 的工作若排在後面，前面每一次「回歸逐筆相同」的驗證都只是暫時有效。**

| **G2** | API 介面收斂 | **✅ 已完成**（2026-08-08，策略層資料欄位抽象化整份移出）——`core/api/` 已提供具名查詢方法，G3 的還原價可直接掛 adjusted 變體 |

### G4 提前施作的實際順序與其後果（2026-08-07）

原規劃為 `G1 → G2 → G3 → G4`，實際施作為 **`G1 → G4 → G2`**（G2 於 2026-08-08 完成），G3 尚未動工。

- **為什麼可以**：G4 全程「行為零改變」，17 個步驟每一步都以**當時**的 baseline 驗證逐筆相同，因此其正確性不依賴 baseline 的內容為何。
- **後果**：G3 重產 baseline 之後，G4 那 17 次「逐筆相同」的驗證即成為歷史紀錄——但那是**刻意的行為變更**（還原價與成本口徑），不是回歸。重產後只需確認新 baseline 可被穩定重現即可，不需要回頭重驗 G4。
- **仍然成立的原則**：G3 的兩份工作（股價還原、LONG 成本口徑）必須**合併排程、只重產一次 baseline**，否則會產生兩輪逐筆歸因。

### 關於「專案工程基建補齊」的延後決定（2026-08-07）

該份原列為 G1（`pyproject.toml` → `ruff` → CI）。經確認 **G2~G5 對它沒有任何硬相依**——三處宣稱的依賴（`策略層資料欄位抽象化` S6 防護測試、`部位控管` S2 測試、Phase0-1 快照納入 CI）全是「有了更好」而非「沒有做不了」——故改列 `∥`，**不阻塞任何梯次**。

延後的取捨：

- **失去**：引擎重構 17 步的回歸驗證失去自動兜底，全靠人工記得跑。
- **替代**：改由多市場抽象 **Phase0-1 產出一鍵回歸腳本**（`scripts/run_regression.sh`，同時跑 SHORT 秒級快照與 LONG 915 筆），成本 10 分鐘，不需 `pyproject.toml` 與 GitHub Actions。**G1 的護欄性質因此仍然成立。**
- **附帶好處**：S2 的全專案格式化會動到大量檔案，若在重構前做，多市場抽象又會重寫同一批檔案，`git blame` 等於被洗兩次；放到重構後只洗一次。
- **建議落點**：不晚於 G6 動工前（期貨／美股會新增大量檔案，屆時沒有 `ruff` 與 CI 的代價會開始放大）。

> 此處正是「優先級 ≠ 梯次」的實例：該份仍是 **P1**（重要性未變），但梯次為 `∥`（本次不排進關鍵路徑）。

## 維護規則

1. 每次**新增**待辦 `.md`，同步在上表新增一列，並填寫優先級、狀態、梯次、說明與相依。
2. 每次**實作**推進（子任務完成、狀態欄變更），同步更新該列的「狀態」與「進度」。
3. 項目完成並整份移出 `backlog/` 時，刪除本表對應那一列（移出方式見 [`manage-backlog` skill §5](../.claude/skills/manage-backlog/SKILL.md#5-完成後的處理)）。
4. 優先級為當下研判結果，可隨需求調整，但調整後必須讓本表與各文件內的優先序敘述一致。
5. **梯次為相依關係的推導結果，不可單獨調整**：若要改動某列的梯次，必須先確認該文件的前置相依確實改變，並同步更新〈執行梯次〉一節的流程圖與衝突清單。一份文件的不同步驟可分屬不同梯次（以 `／` 分隔），此時須在「相依」欄寫明哪些步驟屬哪一梯。
