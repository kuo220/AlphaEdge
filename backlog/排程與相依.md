# Backlog 排程與相依

本檔記錄 `backlog/` **跨文件**的執行順序、相依判斷與施作紀錄，由 [`index.md`](index.md) 的〈梯次〉欄引用。

> **本檔不是待辦事項**：不描述任何要實作的工作，因此不列入 `index.md` 的待辦清單，也不適用 [`manage-backlog` skill §2](../.claude/skills/manage-backlog/SKILL.md) 的「Abstract ＋ 進度追蹤表 ＋ 步驟詳述」結構。`index.md` 只保留通則（狀態圖例、優先級與梯次定義、待辦清單），會隨施作變動的排程敘事一律寫在這裡。

---

## 一、為什麼要分「優先級」與「梯次」

**優先級回答「多重要」，梯次回答「什麼時候能動工」，兩者不同**——高優先級的工作可能因為前置未完成而不能先做。

梯次的排序依據**不是**重要性，而是「誰會讓 `test_long_regression_snapshot` 失效」。
（該 baseline 已於 2026-08-15 由 915 筆／半年 重產為 **1,889 筆／2024 全年**，並改以還原價計算訊號。）這條 baseline 是全 `backlog/` 的共用資產：部位控管（✅）、策略層欄位抽象（✅）、執行真實度，全部拿它當驗收條件。**會換掉 baseline 的工作若排在後面，前面每一次「回歸逐筆相同」的驗證都只是暫時有效。**

## 四、施作紀錄

### 4.1 G4 提前施作的實際順序與其後果（2026-08-07）

原規劃為 `G1 → G2 → G3 → G4`，實際施作為 **`G1 → G4 → G2`**（G2 於 2026-08-08 完成），G3 尚未動工。

- **為什麼可以**：G4 全程「行為零改變」，17 個步驟每一步都以**當時**的 baseline 驗證逐筆相同，因此其正確性不依賴 baseline 的內容為何。
- **後果**：G3 重產 baseline 之後，G4 那 17 次「逐筆相同」的驗證即成為歷史紀錄——但那是**刻意的行為變更**（還原價與成本口徑），不是回歸。重產後只需確認新 baseline 可被穩定重現即可，不需要回頭重驗 G4。
- **仍然成立的原則**：G3 的兩份工作（股價還原、LONG 成本口徑）必須**合併排程、只重產一次 baseline**，否則會產生兩輪逐筆歸因。

### 4.4 G3 結清（2026-08-15）

`股價還原與除權息調整` 五步全數完成並移出 `backlog/`：除權息 ETL（兩市場皆官方來源）、
還原方式選型、還原查詢與報價路徑、baseline 重產、文件。**還原已改為預設啟用**
（`build_backtester(adjusted_price=True)`）。

baseline 一併由「2024 上半年 915 筆」延長為「**2024 全年 1,889 筆**」——原區間經實測
對還原完全無感（台股除權息 67.2% 集中在下半年），沿用等於留下一條偵測不到還原行為的回歸線。

**G3 至此結清，`backlog/` 內已無任何會動到 baseline 的工作。**

### 4.3 `LONG 成本口徑收斂` 移出 G3（2026-08-15）

該份原被歸類為 G3，理由是「會讓 LONG baseline 失效」。以
`tests/backtest/compare_cost_formula.py` 掃 2,448 組後證明該假設**不成立**：

- 兩套公式的差異 **100% 落在部分平倉**（其中 91.7% 觸及最低手續費 20 元門檻）；
- LONG baseline 的 915 筆**全部是全額平倉**，該情境下兩套公式四項數值逐格相同。

實作後回歸雙線確實逐筆通過，本份因此是**行為零改變的重構**，四步已全數完成並移出
`backlog/`。**G3 現在只剩「股價還原」S4 一項會動到 baseline**，原本「兩份合併、只重產一次」
的排程限制隨之解除。

### 4.2 關於「專案工程基建補齊」的延後決定（2026-08-07）

該份原列為 G1（`pyproject.toml` → `ruff` → CI）。經確認 **G2~G5 對它沒有任何硬相依**——三處宣稱的依賴（`策略層資料欄位抽象化` S6 防護測試、`部位控管` S2 測試、Phase0-1 快照納入 CI）全是「有了更好」而非「沒有做不了」——故改列 `∥`，**不阻塞任何梯次**。（前兩項所屬的文件已分別於 2026-08-08、2026-08-09 完成並移出，該判斷獲得驗證。）

延後的取捨：

- **失去**：引擎重構 17 步的回歸驗證失去自動兜底，全靠人工記得跑。
- **替代**：改由多市場抽象 **Phase0-1 產出一鍵回歸腳本**（`scripts/run_regression.sh`，同時跑 SHORT 秒級快照與 LONG 915 筆），成本 10 分鐘，不需 `pyproject.toml` 與 GitHub Actions。**G1 的護欄性質因此仍然成立。**
- **附帶好處**：S2 的全專案格式化會動到大量檔案，若在重構前做，多市場抽象又會重寫同一批檔案，`git blame` 等於被洗兩次；放到重構後只洗一次。
- **建議落點**：不晚於 G6 動工前（期貨／美股會新增大量檔案，屆時沒有 `ruff` 與 CI 的代價會開始放大）。

> 此處正是「優先級 ≠ 梯次」的實例：該份仍是 **P1**（重要性未變），但梯次為 `∥`（本次不排進關鍵路徑）。

## 七、維護規則

1. **梯次為相依關係的推導結果，不可單獨調整**：要改動 `index.md` 某列的梯次，必須先確認該文件的前置相依確實改變，並同步更新本檔 §2 定義表與 §3 流程圖。
2. 一份文件的不同步驟可分屬不同梯次（`index.md` 以 `／` 分隔），此時須在該列「相依」欄寫明哪些步驟屬哪一梯。
3. 排程判斷改變（提前、延後、阻塞解除）時，在 §4 補一則帶**絕對日期**的紀錄，不要只改結論。
4. 衝突解除後不要刪掉 §5 的條目，改用刪除線標記並註明解除日期與理由。
