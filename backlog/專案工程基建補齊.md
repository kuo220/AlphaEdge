# 專案工程基建補齊

## Abstract

- **背景／問題**：專案的**程式碼品質規範完整**（`CLAUDE.md` §2 有 10 節 coding style、`.cursor/rules/` 有對應規則），但**沒有任何自動化在執行這些規範**：無 `pyproject.toml`（`import core` 依賴當前工作目錄，`tests/backtest/conftest.py:8-9` 必須手動 `sys.path.insert`）、無 `ruff.toml`／`pre-commit`（`CLAUDE.md` §2.10 寫明行寬 88／雙引號但無設定檔可執行）、無 CI（沒有 `.github/`）。`requirements.txt` 把 105 個 transitive dependency 全部 pin 死，等於當 lock file 用，但沒有 direct dependency 的來源可追。此外 `core/config.py` 有 import 時副作用（`load_dotenv()` 於 :9、`LOGS_DIR_PATH.mkdir()` 於 :32），只要 import 就會寫檔案系統。
- **目標**：讓 `CLAUDE.md` 的規範由工具自動執行而非人工記憶；讓專案可 `pip install -e .` 安裝；讓每次 push 自動跑 lint ＋ 快速測試。**這件事與所有重構正交**，做完之後所有重構的信心度都會上升。
- **範圍界線**：**不改任何 `core/` 的業務邏輯**。**不做**：切換套件管理器到 Poetry／uv（維持 pip ＋ venv）、不做 Docker 映像優化（`docker-compose.yml` 現況可用）、不做測試覆蓋率提升（只建立基線與報告，不追指標）、不做 `dev/env/*.yml`（conda 環境檔）的整併。
- **驗收標準**：`pip install -e .` 後於任意目錄可 `import core`；`ruff check .` 與 `ruff format --check .` 通過；GitHub Actions 於 push 時自動跑 `ruff` ＋ `pytest -m "not slow"` 並全綠；`tests/backtest/conftest.py` 的 `sys.path.insert` 可刪除。

> **時機（2026-08-07 修訂）**：原建議 S1~S3 在 [回測引擎多市場抽象.md](回測引擎多市場抽象.md) 動工**之前**完成。經確認 **G2~G5 對本份沒有任何硬相依**——三處宣稱的依賴（[策略層資料欄位抽象化.md](策略層資料欄位抽象化.md) S6 的防護測試、[部位控管下沉引擎.md](部位控管下沉引擎.md) S2 的純記憶體測試、Phase0-1 快照納入 CI）全都是「有了更好」而非「沒有做不了」——故本份改列梯次 `∥`，**不阻塞任何梯次**。
>
> - **護欄職責的替代**：引擎重構的回歸把關改由多市場抽象 **Phase0-1 產出的一鍵回歸腳本**（`scripts/run_regression.sh`）承擔，成本 10 分鐘，不需 `pyproject.toml` 與 GitHub Actions。
> - **延後 S2 反而更合理**：全專案格式化會動到大量檔案，若在重構前做，多市場抽象又會重寫同一批檔案，`git blame` 等於被洗兩次；放到重構後只洗一次。
> - **建議落點**：不晚於 G6（期貨／美股／PostgreSQL）動工前。那些工作會新增大量檔案，屆時沒有 `ruff` 與 CI 的代價會開始放大。
> - 本份仍為 **P1**——重要性未變，只是本次排程不進關鍵路徑。

## S1. `pyproject.toml` 與可編輯安裝 ⬜

- **目的**：讓 `core` 成為真正的 package，解除「只能從 repo root 執行」與「測試要手動改 `sys.path`」兩個限制。
- **做法**：
  1. 新增 `pyproject.toml`，使用 setuptools backend（不引入新套件管理器）：
     ```toml
     [project]
     name = "alphaedge"
     version = "0.1.0"
     requires-python = ">=3.12"
     dependencies = [
         "pandas>=3.0",
         "numpy>=2.4",
         "loguru>=0.7",
         "python-dotenv>=1.2",
         # …只列「直接 import 的套件」
     ]

     [project.optional-dependencies]
     dev = ["pytest>=9.0", "pytest-timeout>=2.4", "ruff", "pytest-cov"]
     ```
  2. **相依清單以實際 import 為準**：用 `grep -rhoE '^(import|from) [a-z_]+' --include="*.py" core/ tasks/ frontend/ | sort -u` 產出直接相依清單，不要照抄 `requirements.txt`。
  3. 現行 `requirements.txt` 改名為 `requirements-lock.txt` 保留（既有 Docker build 與 conda 環境仍可用），`requirements.txt` 改為一行 `-e .`。
  4. 把 `pytest.ini` 的內容併入 `pyproject.toml` 的 `[tool.pytest.ini_options]`，刪除 `pytest.ini`。
  5. 刪除 `tests/backtest/conftest.py:8-9` 的 `sys.path.insert`。
- **產出**：`pyproject.toml`、`requirements.txt`、`requirements-lock.txt`、`tests/backtest/conftest.py`；`pytest.ini` 刪除。
- **驗證方式**：建立乾淨 venv → `pip install -e ".[dev]"` → 於 `/tmp` 下執行 `python -c "import core; print(core.__file__)"` 成功；`pytest -m "not slow"` 全數通過。
- **相依**：無。須確認 `core/Dockerfile`、`frontend/Dockerfile` 的安裝步驟同步調整。

## S2. `ruff` 設定並全專案套用 ⬜

- **目的**：把 `CLAUDE.md` §2.5（import 排序）、§2.10（行寬 88、雙引號、magic trailing comma）從文字規範變成可執行檢查。
- **做法**：
  1. 於 `pyproject.toml` 新增設定，對齊既有風格：
     ```toml
     [tool.ruff]
     line-length = 88
     target-version = "py312"

     [tool.ruff.lint]
     select = ["E", "F", "I", "UP", "B", "BLE", "TRY"]
     # UP006/UP035：專案規範要求 typing.List/Dict（CLAUDE.md §2.4.3），必須關閉
     ignore = ["UP006", "UP035"]

     [tool.ruff.format]
     quote-style = "double"
     ```

     - **`BLE`（blind-except）與 `TRY` 是刻意加的**：`core/` 目前 108 個 `except` 中有 81 個是 `except Exception` 或裸 `except`（**75%**），而 `core/pipeline/utils/exceptions.py` 已經定義了自訂例外卻沒有普及。ETL 場景下這會把「網路逾時」（該重試）與「資料 schema 變了」（該中止）混為一談。
     - 本步驟**只負責量化，不負責修**：預期這兩條規則會噴出大量告警，先以 `--statistics` 產出分佈（哪些模組最集中），把數字記入本文件 §例外處理現況，再決定是「逐一修」還是「另開 backlog」。若數量過大擋住 S3 的 CI 落地，可先將這兩條移入 `ignore` 並在本文件註明，**不要為了讓 CI 變綠而把它們永久關掉**。
  2. `ruff check --fix` ＋ `ruff format` 全專案跑一次。
  3. **格式化的改動要單獨一個 commit**，且該 commit 不含任何邏輯變更——否則日後 `git blame` 與 code review 都會被洗掉。
- **產出**：`pyproject.toml`；全專案格式化 commit。
- **驗證方式**：
  1. `ruff check .` 與 `ruff format --check .` 皆通過。
  2. **格式化 commit 前後，LONG 回歸 915 筆逐筆相同**（純格式化理應零影響，但這是最便宜的保險）。
- **相依**：S1。
- **注意**：`ignore` 清單裡的每一條都要註明對應的 `CLAUDE.md` 章節，避免日後有人「順手」打開而與專案規範打架。

## S3. GitHub Actions CI ⬜

- **目的**：讓 lint 與快速測試在每次 push 自動執行，重構時不必依賴人工記得跑。
- **做法**：新增 `.github/workflows/ci.yml`：
  ```yaml
  on: [push, pull_request]
  jobs:
    check:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-python@v5
          with:
            python-version: "3.12"
        - run: pip install -e ".[dev]"
        - run: ruff check .
        - run: ruff format --check .
        - run: pytest -m "not slow" --timeout=300
  ```
  - **只跑 `-m "not slow"`**：`test_long_regression_snapshot` 需要 `stock.db`（未進版控，`.gitignore` 有 `*.db`），CI 環境沒有資料庫。
  - 因此需先確認 `pytest.ini` 的 `slow` marker **已正確標註在所有需要 DB 的測試上**；未標註者會在 CI 失敗，這也正好是一次盤點。
  - `shioaji`／`finmind` 等需要 API 金鑰的測試同樣須標記為 `slow` 或另加 marker。
- **產出**：`.github/workflows/ci.yml`；必要時補標 `@pytest.mark.slow`。
- **驗證方式**：push 後 workflow 全綠；故意引入一個格式錯誤，CI 應變紅。
- **相依**：S1、S2。
- **後續**：[回測引擎多市場抽象.md](回測引擎多市場抽象.md) Phase0-1 的 SHORT 快照是**純記憶體、秒級**，完成後應納入 CI，讓引擎重構在 CI 就有一條回歸線把關。

## S4. 移除 `core/config.py` 的 import 副作用 ⬜

- **目的**：`import core.config` 不應該產生任何檔案系統與環境變數的副作用。現況下任何 import 該模組的測試都會被動建立 `core/logs/`，且 CI 無 `.env` 時 `load_dotenv()` 的行為不明確。
- **做法**：
  1. 移除 `core/config.py:32` 的 `LOGS_DIR_PATH.mkdir(parents=True, exist_ok=True)`，改由 `core/utils/log_manager.py` 的 `LogManager.setup_logger()` 在**實際要寫檔時**惰性建立。
  2. `load_dotenv()`（:9）保留，但確認 `.env` 不存在時不會拋錯（`python-dotenv` 預設行為即為靜默略過，需實測確認），並在 CI 用環境變數而非檔案提供必要設定。
  3. 檢查其他 module-level 副作用：`DDB_PORT: int = int(os.getenv("DDB_PORT") or "0")`（:186）在環境變數為非數字字串時會於 import 期拋 `ValueError`，應加防護。
- **產出**：`core/config.py`、`core/utils/log_manager.py`。
- **驗證方式**：
  1. 刪除 `core/logs/` 後執行 `python -c "import core.config"`，目錄**不應**被建立；執行任一會寫 log 的流程後，目錄應被建立。
  2. LONG 回歸 915 筆逐筆相同。
- **相依**：S1。

## S5. `pre-commit` 掛鉤 ⬜

- **目的**：讓 S2 的格式成果在本機就被維持，而不是等到 CI 才發現。
- **做法**：新增 `.pre-commit-config.yaml`，掛 `ruff` 與 `ruff-format`（官方 `astral-sh/ruff-pre-commit`），另加 `check-added-large-files`（`tick.png` 有 512KB，雖已被 `.gitignore` 排除，但此掛鉤能防止類似檔案再進來）。
- **產出**：`.pre-commit-config.yaml`；`README.md` 補一行安裝說明（`pre-commit install`）。
- **驗證方式**：`pre-commit run --all-files` 通過；故意提交格式錯誤的檔案會被擋下。
- **相依**：S2。**此步驟為可選**，未做不影響 S1~S4 的驗收。

## S6. 測試覆蓋率基線 ⬜

- **目的**：知道目前測到哪、沒測到哪，作為後續補測試的依據。**不設門檻**——在覆蓋率明顯偏低時設門檻只會鼓勵寫無效測試。
- **做法**：
  1. `pyproject.toml` 新增 `[tool.coverage.run]`（`source = ["core"]`、`omit` 掉測試與腳本目錄（原本要 omit 的 `core/api/old api/` 已於 2026-08-07 由多市場抽象 Phase4-3 刪除））。
  2. 在 CI 加一步 `pytest --cov=core --cov-report=term-missing -m "not slow"`，允許失敗不阻擋（`continue-on-error`）。
  3. 把首次量測結果記入本文件 §覆蓋率基線，含**分模組**數字。
- **產出**：`pyproject.toml`、`.github/workflows/ci.yml`、本文件 §覆蓋率基線。
- **驗證方式**：報告可產出；數字記入文件。
- **相依**：S3。
- **預期發現**（撰寫本文件時的觀察，待 S6 量測確認）：`core/backtest/` 有 8 個測試檔、覆蓋較完整；`core/strategies/`、`core/api/`、`frontend/` 幾乎為 0。補測試本身不在本份範圍，應依基線結果另開 backlog。
