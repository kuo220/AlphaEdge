# 股價還原與除權息調整

## Abstract

- **背景／問題**：`price` 表存的是 TWSE／TPEX 每日行情的**原始成交價**（欄位為 `開盤價`／`收盤價`／`漲跌價差`），cleaner 未做任何還原。除權息造成的價格跳空因此被回測當成真實漲跌——放空部位在除息日**憑空獲利**、做多部位**憑空虧損**。高殖利率股（5~8%）單日的虛假損益可以直接蓋過一次當沖的真實獲利。這不是放空專屬問題，**所有既有 LONG 策略的歷史回測都受污染**。
- **目標**：讓回測讀到的價格序列在除權息前後連續，使「價格變化」只反映真實的市場漲跌；並保留原始價供下單價格、漲跌停與檔位判定使用。
- **範圍界線**：**不做**股利補償現金流與停券強制回補（屬 [放空回測市場約束補齊.md](放空回測市場約束補齊.md) S3，與本文件共用資料源但解不同問題）；**不做** tick 表的還原（`tick` 為當日盤中資料，跨日還原無意義，僅需在文件標明）；**不改**回測引擎的成本與記帳邏輯，只換價格來源。
- **驗收標準**：任選 10 檔高殖利率股，除息日的還原後價格變化與「實際漲跌幅」一致（誤差在檔位內）；LONG 回歸 baseline 重產後，差異**可完全歸因於除權息還原**（逐筆比對，不得出現無法解釋的差額）；下單價格與漲跌停判定仍使用原始價，未因還原而失真。

### 已知限制：上市的現金股利／配股率在「權息並存」時無法拆分

**只影響上市**。櫃買中心直接提供 `現金股利` 與 `每仟股無償配股`，上櫃 1060 筆**無一筆缺值**。

- **現象**：證交所 `TWT49U` 只有「權值+息值」合計，須由「減除股利參考價」推導，但該欄語意不一致——純除息時等於除權息參考價、純除權時等於除權息前收盤價，**權息並存時兩種寫法都出現**（2024 年 62 筆權息列中有 57 筆等於參考價）。
- **後果**：若硬套 `現金股利 = 前收盤價 − 減除股利參考價`，會把股票股利整包誤算成現金股利。
- **處置**：`StockDividendCleaner.split_dividend()` 對上市**只在語意明確時填值**（純除息、或純除權且減除股利參考價等於前收盤價），其餘留 `NULL` 並記錄筆數。2024 年上市 1184 筆中有 **85 筆為 `NULL`**（權息並存 62 ＋ 含現金增資的純除權 23）。
- **對本文件的影響**：**無**。還原係數只用到前收盤價與參考價，與拆分無關。
- **對 [放空回測市場約束補齊.md](放空回測市場約束補齊.md) S3 的影響**：股利補償需要現金股利，**上市**權息並存的標的會取到 `NULL`，該步驟動工時須另接股利政策資料源或明確拒絕處理該類標的；上櫃不受影響。

## S2. 還原方式選型 ✅

- **目的**：先定案「還原價從哪裡來」，S3 才有明確的實作目標。三種做法的取捨差異很大，不可邊做邊改。
- **做法**：三選一——
  - **做法 A：`price` 表新增還原欄位**（`還原開盤價`／`還原收盤價`…）。查詢最快，但**每次有新的除權息就必須回頭重算該股全部歷史**（還原係數是往前累乘的），且 SQLite 全表更新成本高。
  - **做法 B：查詢時即時還原**（`StockPriceAPI` 內以除權息表計算係數）。無須改資料表、無歷史重算問題，但每次查詢都要 join 與累乘，回測逐日查詢的效能需實測。
  - **做法 C：獨立的還原價表**（`price_adjusted`）。兼具查詢速度與原始資料不可變，代價是多一份需要同步的資料與一次全量重建流程。
  - **建議**：先實測 B 的效能（以 2020~2025 五年、單策略全市場日查詢為基準）；若可接受即採 B，因為它唯一不會產生「還原價與原始價不同步」的資料一致性問題。
  - **還原方向的決策**：業界主流為**後復權**（以最早日為基準往後調整，歷史價格不變）或**前復權**（以最新日為基準往回調整，最新價等於真實價）。回測建議用**後復權**——前復權會讓同一個歷史日期的價格隨著時間改變，導致 baseline 每次除權息後都失效。
- **產出**：決策與理由寫回本文件。
- **驗證方式**：三種做法的效能實測數字 ＋ 資料一致性風險評估，寫入本文件後方可進入 S3。
- **相依**：S1（需先知道除權息資料的量級）。

### 決策（2026-08-08）：採**做法 B（查詢時即時還原）＋ 後復權**

- **為什麼是 B**：它是唯一不會產生「還原價與原始價不同步」的做法。A 與 C 都需要在每次有新的除權息時回頭重算該股全部歷史（還原係數是往前累乘的），一旦某次重算漏跑，資料庫裡就會同時存在兩個世代的還原價，而且**不會有任何錯誤訊息**——這正是本專案反覆要避免的靜默失效。
- **為什麼是後復權**：前復權會讓同一個歷史日期的價格隨著時間改變，導致 LONG baseline 在每次除權息後自動失效，回歸保護等於形同虛設。
- **效能疑慮如何處理**：G2（2026-08-08 完成）已把策略的價格取用收斂成 `get_close_map()` 這類**每日一次**的對照表查詢，還原係數只需在同一個方法內套用一次，不是逐檔累乘——B 的效能疑慮因此大幅下降。S3 實作時仍須以 2020~2025 五年單策略全市場日查詢實測並把數字補回本節。
- **實作落點**：`StockPriceAPI` 新增 `get_adjusted_*` 系列，與既有 `get_close_map()`／`get_close_series()` 一一對應。**不要**讓同一個方法依參數回傳兩種語意的價格（見 S3）。

### 效能實測（2026-08-15）：做法 B 確認可行

以規格要求的基準測量——2020~2025 共 **1,459 個交易日**、每日全市場對照表查詢：

| 項目 | 耗時 | 每日 |
|------|------|------|
| 原始價 `get_close_map()` | 10.74 秒 | 7.36 ms |
| 還原價 `get_adjusted_close_map()` | 13.00 秒 | 8.91 ms |
| 還原係數表載入（**整個 process 一次**） | 0.24 秒 | — |

**額外成本 +2.26 秒（+21%）**，六年回測多花兩秒，做法 B 的效能疑慮解除。

關鍵在於係數表**整表只載入一次**（23,972 筆、0.24 秒）並以 `np.searchsorted` 定位，
而非每次查詢都 join 除權息表累乘——後者才是 S2 當初擔心的成本。

## S3. 還原價落地與讀取路徑 ✅

- **目的**：讓回測讀到還原價，同時保留原始價供下單與漲跌停判定使用。
- **做法**：
  - **關鍵區分（實作前必讀）**：還原價與原始價**用途不同，不可混用**——

    | 用途 | 該用哪個 | 理由 |
    |------|----------|------|
    | 策略的訊號計算（漲跌幅、均線、動能） | **還原價** | 這是本文件要解的問題 |
    | 成交價與成本計算 | **原始價** | 手續費、稅是對實際成交金額課徵 |
    | 漲跌停區間判定（`validate_fill_price`） | **原始價** | 漲跌停以實際掛牌價計算；除權息日的基準須改用**除權息參考價**而非前一日收盤 |
    | 價格檔位（`round_to_tick`） | **原始價** | 檔位依實際價格分段 |
  - `StockPriceAPI` 提供明確區分的查詢方法（例如 `get()` 維持原始價、新增 `get_adjusted()`），**不要**讓同一個方法依參數回傳兩種語意的價格。
  - `StockQuoteAdapter` 需決定 `StockQuote` 攜帶哪一組價格，或同時攜帶兩組（建議後者：新增 `adj_close` 等欄位，預設為 `None` 時退回原始價，確保既有策略行為不變）。
  - `Backtester.update_prev_close()` 在除權息日應改用**除權息參考價**作為次日漲跌停基準，否則區間整段偏移。
- **產出**：`core/api/stock_price_api.py`、`core/adapters/`、`core/models/stock/quote.py`、`core/backtest/backtester.py`。
- **驗證方式**：取 10 檔高殖利率股，除息日的還原價變化幅度與實際漲跌幅一致；同日的成交價、手續費、漲跌停判定仍走原始價（各一組測試）。
- **相依**：S1、S2。

### 施作紀錄（2026-08-15）：API 層完成

**已完成**：

### 剩餘工作

**實查發現（2026-08-15）**：`core/strategies/stock/momentum_strategy_1.py:100` 的漲跌幅算式為

```python
price_chg = (stock_quote.close / yesterday_close_price - 1) * 100
#            ↑ 來自 StockQuote（adapter）      ↑ 來自 get_close_map（API）
```

**今日價格走 `StockQuote`、昨日價格走 API，是兩條不同的路徑**。因此還原必須「成對」施作——只改 API 那一半，算出來的比值會同時混用還原價與原始價，比不還原更糟，而且不會報錯。

### 施作紀錄（2026-08-15）：除權息日的漲跌停基準

**落點與原規劃不同**：原本預計把 `StockDividendAPI` 注入 `TwStockFillModel`，實作時改為
**由 `DataFeed` 提供、引擎轉交、`FillModel` 套用**三段，理由是 model 層不應持有資料 API
（`FillModel` 至今沒有任何 DB 相依，開這個先例會讓後續 model 跟進）。

| 層 | 新增 | 說明 |
|----|------|------|
| `BaseDataFeed` | `get_price_limit_basis(date)` | 預設回傳 `{}`，不支援公告基準的市場不需實作 |
| `TwStockDataFeed` | 覆寫上述方法 | 轉呼叫 `StockDividendAPI.get_opening_reference_price_map()` |
| `BaseFillModel` | `apply_price_limit_basis(basis)` | 預設 no-op |

| `Backtester.execute_bar()` | 於下任何單之前呼叫 | 兩條路徑（DAY／TICK）共用 |

**影響量化**：2024 年 2244 筆除權息中，**2138 筆（95.3%）的漲跌停區間會改變**。
以聯發科 2024-01-04 為例：前收 953 算出 `[858, 1045]`，改用開盤競價基準 928 後為
`[836, 1020]`，**與交易所公告值完全相同**。

**LONG baseline 未受影響**：全歷史 23,972 筆比對顯示修正方向無誤（與官方公告漲跌停的相符率
由 0.1% 提升到 54.5%），但 `momentum_strategy_1` 以收盤價成交，幾乎不會落在漲跌停邊界上，
故 2024 回歸逐筆相同。**回歸保護線因此得以保留到 S4**，不需要提前重產。

### 施作中發現的既有缺陷（不屬本文件範圍，須另立工作）

兩者都在 `TwStockSpec.get_price_limits()`，與除權息無關，是**既有的漲跌停計算問題**：

1. **2015-06-01 前的漲跌停幅度應為 7%，程式寫死 10%**
   實測官方公告值：2015-06-01 前中位數 **6.92%**、之後 9.91%（台股當日放寬）。
   `PRICE_LIMIT_RATIO` 為固定值，**2013-01 ~ 2015-05 的回測漲跌停區間全數偏寬約 43%**。
   相符率佐證：2013、2014 兩年與官方公告值相符率為 **0.0%**。

2. **檔位對齊規則與官方有出入**
   2015 年後相符率僅 50~75%，代表約四分之一到一半的案例與官方差一個檔位。
   現行做法是「基準 ±10% 後往內對齊檔位」，與交易所實際的升降單位取值規則不完全一致。

**影響範圍**：漲跌停只在 `FillModel.validate()` 用於拒單，多數訂單不在邊界上，故對既有回測
結果影響有限；但放空的「漲停無法回補」判定（`check_limit_up_locked`）直接依賴此邏輯，
`limit_up_cover_failed` 事件計數會失真。建議併入
[回測引擎執行真實度補強.md](回測引擎執行真實度補強.md) 處理。

## S4. 影響評估與 LONG baseline 重產 ⬜

- **目的**：還原價會改變所有既有策略的訊號，LONG 回歸 baseline 必然失效。必須讓「差異可完全歸因」，否則之後所有重構都失去回歸保護。
- **做法**：
  - **順序不可顛倒**：先在**不啟用**還原的情況下確認 baseline 仍逐筆相同 → 再啟用還原重產 baseline → **單獨 commit**，不得與功能變更混在同一個 commit（放空框架 §9.0 的既有約定）。
  - 差異歸因：逐筆比對重產前後的交易清單，每一筆差異都要能對應到「某檔股票在某個除權息日的訊號變化」。若出現無法解釋的差額，代表 S3 有實作錯誤。
  - 順帶量化影響：統計「因除權息虛假跳空而產生的開倉」在原 baseline 中佔多少比例——這個數字直接說明本文件的價值，值得寫進文件。
- **產出**：`tests/backtest/snapshots/momentum_strategy_1_baseline.csv`、影響評估數字寫回本文件。
- **驗證方式**：重產後 `test_long_regression_snapshot` 通過；差異歸因表列於本文件。
- **相依**：S3。
