### S1. loguru 的 traceback 寫法（15 處）✅

- **目的**：`logger.error(f"...{e}", exc_info=True)` 是 **`logging` 標準庫**的寫法。loguru 的 `logger.error(message, *args, **kwargs)` 把多餘的 kwargs 當成 `str.format()` 的參數，訊息裡沒有 `{exc_info}` 佔位符時就**默默丟掉**——traceback 從來沒有被印出來過。
- **實證**（2026-09-04）：

  ```python
  logger.error(f"A: exc_info 寫法 -> {e}", exc_info=True)      # 只印一行訊息
  logger.opt(exception=True).error(f"B: loguru 正確寫法 -> {e}")  # 訊息 ＋ 完整 Traceback
  ```

  輸出確認 A 沒有任何 traceback、B 有。全專案 `exc_info=True` **15 處**、
  `logger.opt(exception=` **0 處**。

- **為什麼值得單獨做**：這 15 處全部在**失敗路徑**上，而且集中在最需要事後追查的地方——
  `stock_tick_updater.py`（6 處，含 `Database loading failed`）、
  `finmind/broker_trading_updater.py`／`broker_trading_loader.py`（4 處）、
  `stock_tick_cleaner.py`、`reference_table_loader.py`、`tasks/load_broker_trading_to_db.py`。
  ETL 半夜跑掛的時候，log 只留下 `Database loading failed: <訊息>`，**堆疊全無**，
  而這正是「ETL 失敗語意與缺口回補」整份工作想要根治的可見度問題——
  那份工作把失敗**語意**修好了，失敗的**現場**卻還是拿不到。
- **做法**：
  1. 15 處一律改為 `logger.opt(exception=True).error(...)`；訊息本身**不需改**
     （`{e}` 保留，opt 只是額外附上堆疊）。
  2. **加護欄**：`pyproject.toml` 的 ruff 沒有現成規則能抓這個（它不是語法錯誤），
     故在 `scripts/check_layer_deps.py` 之外另加一條檢查，或直接在 pre-commit 掛一條
     `grep -rn "exc_info=True" core tasks` 的禁用樣式——**沒有護欄的話這 15 處會再長回來**，
     因為 `exc_info=True` 是標準庫肌肉記憶。
- **產出**：見進度表。
- **驗證方式**：改完在其中一條路徑故意拋錯，確認 log 檔內出現 `Traceback`；
  `grep -rn "exc_info=True" core tasks` 為空。
- **相依**：無。**但 `core/pipeline/tw/updaters/` 與 `loaders/finmind/` 目前有另一份工作
  （權益變動表 ETL）正在改**，動手前先確認那條線的變更已提交，或只改 `logger.*` 那一行避免衝突。

### S2. `compute_information_ratio()` 收斂到 `risk_metrics` ✅

- **目的**：F-068 把 Sharpe／Sortino／Volatility 三個指標改成「以 `daily_equity` 的日報酬為樣本、以 √252 年化」並抽到 `core/backtest/analysis/risk_metrics.py`，**IR 被漏掉**——它還是原來那三個缺陷：
  1. **樣本是每筆交易**（`record.roi`）而非時間序列，交易筆數與時間無關，無從年化；
  2. **沒有年化**；
  3. **基準是寫死的 0.0**：`setup()` 裡 `self.benchmark = "0050"` 但 `self.benchmark_return = 0.0`，
     0050 的報酬**從來沒有被取用過**。而從每一個樣本減去同一個常數**不會改變分母**，
     所以現在的 IR 恆等於 `mean(每筆 ROI) / std(每筆 ROI)`——與「相對基準的超額報酬穩定性」無關。
- **做法**：二擇一，**不要留現狀**：
  - **(A) 做完**：`risk_metrics` 新增 `compute_annualized_information_ratio(returns, benchmark_returns)`，
    吃**兩條**日報酬序列（策略與基準），analyzer 改為由 `StockPriceAPI` 取 0050 的還原價日報酬
    （`adjusted=True`，不要再用 `reporter.STOCK_SPLITS` 那套寫死的分割調整）。
  - **(B) 明確不做**：刪掉 `compute_information_ratio()` 與 `BaseBacktestAnalyzer` 的
    對應 `@abstractmethod`，並在 analyzer 的 class docstring 註明「IR 需要基準序列，
    待 benchmark 資料源接上再補」。
  建議 (A)——基準序列本來就要給 [前端指標與報表同源化.md](前端指標與報表同源化.md) S3 用，
  兩邊共用一份才不會又分岔（F-087 的教訓）。
- **產出**：見進度表。
- **驗證方式**：手算對照測試（與 Sharpe 同款）；`tests/backtest/test_risk_metrics.py` 擴充。
- **相依**：無。與前端同源化 S3 建議同批。

>   假跳空，只是目前只有 0050 被 `stock_split.py` 補起來。策略端若直接用還原價算訊號，
>   遇到分割股會踩到同一個坑。

### S3. `check_day_trade_tax_expiry()` 改看回測區間 ✅

- **目的**：F-060 的處置欄要求兩件事——① `tax()` 加 `date` 參數只在 `[START, EXPIRY]` 內減半；② `check_day_trade_tax_expiry()` **改在回測起訖日落在區間外時警告，而不是看真實今天**。①已完成，②沒做：

  ```python
  if self.config.is_day_trade and datetime.date.today() > DAY_TRADE_TAX_EXPIRY:
  ```

- **影響**：`DAY_TRADE_TAX_EXPIRY` 是 2027-12-31，所以這條警告在 2028 年之前**永遠不會觸發**；
  而回測區間跨過落日日期時（例如拿當沖策略跑到 2028 年）稅率假設已經失效，
  卻沒有任何提示。方向與 F-060 的另一半完全一樣：**稅制邊界要看成交日，不看真實今天**。
- **做法**：`StockCostModel` 取得回測起訖日（由 factory 或 `setup()` 注入），
  區間與 `[DAY_TRADE_TAX_START, DAY_TRADE_TAX_EXPIRY]` 有落差時警告，並指出是哪一段。
  拿不到區間時**維持靜默**而不是退回看 `today()`——寧可不說，也不要說錯。
- **產出**：見進度表。
- **驗證方式**：兩條測試（區間內不警告、區間跨越落日日期會警告）。
- **相依**：無。
