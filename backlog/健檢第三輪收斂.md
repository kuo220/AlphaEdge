## 步驟詳述

### S1. analyzer 四個交易統計補防零除 ⬜

- **目的**：`StockBacktestAnalyzer` 的四個交易統計直接除以可能為零的分母，且**沒有任何一個有防護**：

  ```python
  def compute_win_rate(self) -> float:
      return self.compute_num_winning_trades() / self.compute_num_trades()   # 零筆交易 → 炸

  def compute_win_lose_rate(self) -> float:
      return win_cnt / lose_cnt                                              # 零虧損筆數 → 炸

  def compute_profit_factor(self) -> float:
      return profit / loss                                                   # 零虧損金額 → 炸

  def compute_average_return(self) -> float:
      return total_roi / self.compute_num_trades()                           # 零筆交易 → 炸
  ```

- **實證**（2026-09-05，離線、不連 DB）：

  | 情境 | `win_rate` | `win_lose_rate` | `profit_factor` | `average_return` | `average_holding_days` |
  |------|:----------:|:---------------:|:---------------:|:----------------:|:----------------------:|
  | 零筆交易 | **ZeroDivisionError** | **ZeroDivisionError** | **ZeroDivisionError** | **ZeroDivisionError** | `0.0` ✅ |
  | 兩筆全獲利、零虧損 | `1.0` ✅ | **ZeroDivisionError** | **ZeroDivisionError** | `1.85` ✅ | `3.0` ✅ |

- **為什麼確定是疏漏而不是設計**：同一個類別裡的 `compute_average_holding_days()` 開頭就是
  `if not self.trade_records: return 0.0`。作者想到了其中一個，沒想到另外四個。
- **影響範圍（不要誇大）**：`BaseBacktestAnalyzer` 的 class docstring 寫明「Analyzer 供測試與研究驗算指標，
  正式回測輸出走 `report/reporter.py`」，而 **reporter 端已驗證安全**——
  `get_direction_summary()` 的 `len(wins) / len(group)` 走 `groupby`，groupby 不會產生空組，
  且函式開頭有 `if self.trading_report is None or self.trading_report.empty: return pd.DataFrame()`。
  所以這條**不會影響正式回測報表**，踩到的是拿 analyzer 做研究驗算的人：
  「零虧損筆數」在高勝率策略或短區間回測相當常見，而拿到的是一個沒有訊息的 `ZeroDivisionError`。
- **既有測試為什麼沒抓到**：`tests/backtest/test_risk_metrics.py::test_analyzer_metrics_are_none_without_trades`
  只驗了 `compute_sharpe_ratio`／`compute_sortino_ratio`／`compute_volatility` 三個**風險指標**，
  沒有涵蓋這四個**交易統計**。
- **做法**：
  1. 四個方法的回傳型別改為 `Optional[float]`，分母為零時回 `None`。
     **不要回 `0.0`**——`risk_metrics` 模組已經為同一個問題定過調：
     「零筆交易回 None 而不是 0——『沒有資料』與『風險調整後報酬為零』是兩件完全不同的事」。
     勝率 0% 與「沒有交易可算勝率」必須分得開，`profit_factor = 0` 與「從來沒虧過」更是相反的意思。
  2. 同步改 `core/backtest/analysis/base.py` 的四個 `@abstractmethod` 簽章。
  3. `compute_average_holding_days()` 已回 `0.0`，**一併改為 `None`** 以維持同一類別內的一致口徑；
     若改動有呼叫端風險則維持現狀並在 docstring 註明例外。
- **產出**：見進度表。
- **驗證方式**：兩條測試（零筆交易、零虧損筆數），六個統計都不得拋出且回傳值符合上表；
  `./scripts/run_regression.sh` 通過（analyzer 不在回歸線上，預期零影響）。
- **相依**：無。

### S2. `core/api` 九個死介面結清 ⬜

- **目的**：以 AST 掃出 `core/api/` 的 72 個公開方法後逐一比對全 repo 呼叫點（含 `tests/`），
  **九個是零呼叫且零測試**：

  | 檔案 | 方法 |
  |------|------|
  | `stock_dividend_api.py` | `get_stock_dividend()`、`get_stock_dividend_ratio_map()`、`get_ex_dividend_dates()` |
  | `stock_margin_api.py` | `get_stock_margin()`、`get_stock_short_balance()` |
  | `stock_chip_api.py` | `get_stock_net_chip()` |
  | `futures_chip_api.py` | `get_large_trader()` |
  | `futures_margin_api.py` | `calculate_stock_futures_margin()` |
  | `stock_tick_api.py` | `get_last_tick()` |

- **已實測：它們沒有壞**。除了需要 DolphinDB 的 `get_last_tick()` 之外，八個都以正確簽章實際呼叫過，
  全部正常回傳（例如 `get_ex_dividend_dates()` 回 829 個日期、`get_large_trader()` 回 10 個欄位）。
  所以這條不是「壞掉的程式碼」，是**無主的介面**：沒有呼叫端、沒有測試，
  下一次資料表欄位一改，它們會安靜地跟著壞，而沒有任何東西會紅。
- **對照組（刻意不動）**：另有 12 個方法是「只有測試在呼叫、正式程式碼零呼叫」
  （`get_adjust_factor_map`、`get_net_chip`、`get_settlement_map`、`get_open_interest_map`…）。
  `core/api/` 是**策略作者的公開介面**（見 `core/strategies/README.md`），
  有測試就代表有人維護它的行為，這 12 個屬正常狀態，**不在本步驟範圍**。
- **做法**：九個逐一二擇一——
  - **(A) 補測試**：確認它是策略作者會用到的介面，補一條離線或標 `slow` 的測試，
    使其進入前述「有測試的公開介面」那一組；
  - **(B) 刪除**：確認無人需要即刪，並在該檔 docstring 註明「曾有此方法，因無呼叫端於 2026-09 刪除」。

  判準建議：`get_stock_*` 系列（單檔取區間）與 `get_ex_dividend_dates` 明顯是策略會用的形狀，
  傾向 (A)；`calculate_stock_futures_margin()` 與 `get_last_tick()` 需先確認是否已被別的路徑取代，
  否則傾向 (B)。
- **產出**：見進度表。
- **驗證方式**：重跑本步驟用的 AST 掃描腳本，零呼叫零測試的公開方法為 0 個；`pytest -m "not slow"` 全綠。
- **相依**：無。

### S3. 兩個 1.6 MB `.docx` 移出版控 ⬜

- **目的**：`strategy_lab/strategies/tsmc_overnight_signal/reports/` 底下有兩個**程式自動產生**的
  Word 報告在版控裡：

  | 檔案 | 大小 |
  |------|------|
  | `TSMC_OvernightSignal_Quant_Report.docx` | 1,658,559 bytes |
  | `TSMC_OvernightSignal_Quant_Report_EN.docx` | 1,656,314 bytes |

  這是 **F-088 的殘留**：2026-09-04 的「健檢殘留項目收斂」S6 清掉了 13 個 `output/*.html`，
  但**漏了這兩個**——因為 `.gitignore` 第 19 行擋的是 `strategy_lab/**/output/`，
  而這兩個檔在 `reports/`。
- **為什麼會變成問題**：`generate_docx.py` 的 `build_report()` 在不傳 `output_path` 時，
  預設就是寫進**版控中的這兩個路徑**（`_DOCX_ZH`／`_DOCX_EN`），而 `main()` 正是這樣呼叫的。
  也就是說**任何人跑一次報表產生器，就會得到 3.3 MB 的二進位 diff**。
  2026-09-04 實測過：重新產生的檔案與版控中的版本逐字比對，唯一差異是「報告產製日期」那一行——
  內容完全相同，diff 卻是整個檔案。
- **`check-added-large-files` 擋不住**：`.pre-commit-config.yaml` 有 `--maxkb=256` 的掛鉤，
  但那條規則只檢查**新加入**的檔案；這兩個早已被追蹤，與 F-088 的 `.html` 是同一個道理——
  **規則擋不住已經進版控的檔案**。
- **做法**：
  1. `.gitignore` 新增 `strategy_lab/**/reports/*.docx`。
  2. `git rm --cached` 這兩個檔（**檔案留在本機**），commit 一次。
  3. 在 `strategy_lab/strategies/tsmc_overnight_signal/README.md`（若無則於 `generate_docx.py`
     的模組 docstring）註明「報告為產出物，不進版控；需要成品請自行執行 `generate_docx.py`」。
- **產出**：見進度表。
- **驗證方式**：`git ls-files strategy_lab | grep -E '\.(docx|html)$'` 為空；本機兩個檔仍存在；
  重跑 `generate_docx.py` 後 `git status` 乾淨。
- **相依**：無。
